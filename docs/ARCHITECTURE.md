# Mirrorfold: project, architecture, math and code

This document is written for an engineer (or a Claude Code session) picking the project up cold. It describes what the app does, how the code is laid out, the math behind each part, how to test it, and what is known to be weak.

The app is `index.html` (markup), `css/app.css` and about 35 JavaScript modules in `js/` (about 4,500 lines in all, GLSL included). There is no build step and there are no dependencies apart from two Google Fonts. It began as one file; section 17 describes the split.

## 1. What it is

Mirrorfold is a first-person fly-through of endless fractal worlds, rendered by raymarching in a WebGL 1 fragment shader, with a MilkDrop-style feedback and filter chain on top and music reactivity underneath. It is designed for a phone first (touch controls, adaptive resolution) and also works with mouse and keyboard.

Features, in the order a user meets them:

- **31 worlds.** 26 are surfaces found by sphere tracing a distance estimator; 3 (Nebula, Aurora, Lanterns) are volumetric; 2 (Mandelbrot zoom, Julia zoom) are flat pictures (section 6c).
- **Free flight** with six degrees of freedom. Speed scales with distance to the nearest surface, so you cannot hit a wall.
- **Kaleidoscope mirrors**: off, 3, 4, 6, 8 or 12 segments, applied to the ray direction.
- **19 palettes** (8 available at once, 6 unlocked by finding orbs, and 3 near-greys that came with the Biomech world, Vision that came with Seer and Cobalt that came with Net, which are marked `open`, so they need no orb; `ORB_PALS` is the 6).
- **Feedback motions** (6), **filters** (17), **overlays** (10) and **transitions** (8).
- **Music**: a built-in generative track, a user's audio file with a scrubber, the sound of another browser tab, the microphone, or tap tempo for music playing in another app. Three frequency bands drive different parts of the picture.
- **Journey**: an autopilot that flies, and changes world, palette, mirrors, motion, filter and overlay on jittered clocks. What it may change is set by templates; sets play several templates in turn. Both are user-editable and stored in the browser.
- **Orbs** to find, **Share spot** links, and a morphing parameter that makes every world breathe.
- **VR viewer**: side-by-side stereo with gyroscope look, for a phone in a Cardboard-style holder (section 13).

## 2. Running and deploying

Serve the folder with any static web server (`python3 -m http.server`) and open it. It no longer works straight from `file://`, because browsers refuse to load modules from there.

For GitHub Pages: put `index.html`, `css/` and `js/` at the root of the published branch (or in `/docs` if Pages is set to that folder). The empty `.nojekyll` file stops Pages from running Jekyll over the repo. No configuration is needed.

### Full screen on iPhone

Safari on iPhone has no Fullscreen API for pages, so the Fullscreen button hides itself there. The `<head>` carries `apple-mobile-web-app-capable` and related tags so that "Add to Home Screen" opens the page as a standalone web app without browser bars, with `apple-touch-icon.png` (a crop of `docs/worlds.jpg`) as its icon. The viewport uses `viewport-fit=cover` and the status bar style is `black-translucent`, so the canvas runs under the status bar and notch; a block at the end of the `<style>` pads `#hud`, `#adv`, `#start` and `#err` by `env(safe-area-inset-*)`. A home-screen web app has its own `localStorage`, separate from Safari's.

### What changed from the Claude artifact version

The app was built as a Claude artifact, which runs in a sandboxed frame with a strict content security policy. The bundled `index.html` differs from the artifact in one place: **Share spot** now builds its link from `location.href` rather than a hard-coded artifact URL.

Several design decisions were forced by the artifact sandbox and are no longer constraints on GitHub Pages. They are listed here because they explain choices in the code that might otherwise look odd, and because they are the obvious next features:

| Artifact constraint | Effect on the current code | Now possible |
|---|---|---|
| Microphone blocked | There was no live audio input. Tap tempo exists as the workaround for Apple Music and other apps. | Done: the Microphone and Listen to a tab sources (section 10). Both need HTTPS, which Pages provides. |
| Device motion blocked | Look was touch or mouse only. | Done for the VR viewer (section 13). Gyroscope look outside that mode is still open. |

| `alert`/`confirm` blocked | Delete uses a two-tap button. | Unchanged; the two-tap pattern is fine. |
| Per-viewer `localStorage` only | Templates, orb progress and the orbs toggle live in `localStorage`. | Unchanged on Pages. |

**How the modules fit together.** Each file holds function declarations, constants that need nothing from elsewhere, and its own variables. Anything that has to happen when the app starts (building lists, wiring buttons, reading storage, compiling the effect shaders) is in the file's `init()`, and `main.js` calls the `init()`s in a fixed order. Loading a module therefore does nothing by itself, which is why the Node tools can import the cleaners and other pure functions without a page.

**Who owns a value.** Every value is set by exactly one file. Other files read it by importing it (`export let`: importers always see the current value) and change it only by calling that file's functions (`setDetail`, `setWorldNow`, `setPalette`, `landClimb` and so on). Five groups of values that many parts of a frame must change are small state objects, each defined in the file it belongs to: `cam` (camera.js), `tr` (warp.js), `clock` (clock.js), `scene` (choose.js) and `sel` (state.js). A module may not assign to a variable it imports, so this is enforced by the language, not by convention.

**A frame.** `frame()` in `loop.js` is a list of calls: wait for the chip, read the sound, advance the clocks and the transition, measure the distance to the nearest surface, work out the steering, run the autopilot and Journey's clocks, turn and move the camera, move the land, update the orb, the thrown light and the sprites, play or record a flight and place the friends flown with, then draw (with Hold still's two steps either side of the scene, and Save picture's after the last) (`drawScene`, `drawTrails`, `drawBloom`, `drawFinal`). Each step lives in the file that owns what it changes. The steps pass what they work out through one reused object, the frame's notes, called `fr` inside them; the comment above it in `loop.js` lists its fields.

**`__dbg` and `window.MF`.** Every file ends with `__dbg`, an object holding every name in the file (with a getter and a setter for the ones that can change). `main.js` merges them into `window.MF`, and also offers each field of the five state objects by its bare name (`MF.pos` for `MF.cam.pos`). The test tools run their code inside `with(window.MF)`, so it can name any internal variable or function, and so can the browser console (`MF.setLand(1)`). When you add a top-level name to a file, add it to that file's `__dbg` if a test needs it.

The code is still ES5 in style inside the files (`var`, function declarations, no classes).

## 4. Render pipeline

Each frame draws five passes. All use one full-screen triangle and the vertex shader `VS`, which passes `v` (0..1 UV).

```
1. scene     world shader          -> tA        (full resolution)
2. feedback  FS_TRAIL (tA, tT[prev]) -> tT[cur]  (full resolution, ping-pong)
3. bloom     FS_DOWN  (tT[cur])    -> tB[0]     (quarter resolution, bright pass)
             FS_BLUR  horizontal   -> tB[1]
             FS_BLUR  vertical     -> tB[0]
4. final     FS_FINAL (tT[cur], tB[0]) -> screen
5. the eye   FS_EYE   (the finished picture) -> screen   (only while the eye is on: pass 4 then draws into tE; section 8g)
```

Targets are RGBA8 textures with linear filtering and clamped edges, created by `target(w,h)` and recreated in `resize()` whenever the drawing-buffer size changes (which also clears the feedback history). Bloom passes are skipped when bloom strength is zero.

Scene shaders are compiled lazily, one program per world, by `build(w)`, and cached on the world object as `w.prog` and `w.U` (uniform locations). The five post programs are started at start-up and waited for together with the first world's (`progFinish`).

### Programs made ahead of need

Making a program (compiling and linking a shader) is the slowest single thing the page does: a landscape took from a few seconds to over ten on a user's phone, and the page stood still for all of it, because the land was made when it was first turned on.

`js/programs.js` makes a program in two halves. `linkStart` hands the source to the chip and asks nothing back. `linkEnd` asks whether it worked, which is the call that waits. `linkReady` says whether the chip has finished without waiting, through `KHR_parallel_shader_compile` (`par`). `link` is the two halves together, for the small programs made at start-up.

`js/preload.js` uses that. From start-up, also behind the start card, `preloadFrame` (a step of `frame()`) starts one program, looks each frame whether it is ready, finishes it, and starts the next. The order is `preloadOrder`: the landscape in use, the other landscapes in the order the button goes through them, then the worlds after the one in use. The start card shows how far it has got. A world's unfinished program is `w.job` and a landscape's is in `pLandJ`; `build(w)` and `landFinish(k)` finish one that was started, waiting only for what is left of it, so choosing something that is still being made costs no more than before.

**Keeping the page answering.** Measured on a fast desktop chip (headless Chrome with `--use-angle=gl --enable-gpu`), three things made the page slow to answer a press. (1) Start-up made the five effects programs and then the first world's, each waited for in turn: about 0.4 s. `programs.init` now only starts the five (`linkStart`), `choose.init` starts the first world's, and `progFinish` then waits for all six, which the chip makes side by side: the 0.4 s became 0.2 s. What is left of start-up (about 0.45 s there) is the browser making the graphics context and those programs, and no press is answered during it. (2) Finishing a program made ahead of need asked the chip after more than fifty names in one frame, each a short wait: 25 to 40 ms. `linkEndStep`, `buildStep` and `landStep` ask after `PRE_ASK` (6) a frame. (3) The worst: `chipWait` puts a question to the chip every frame, and the chip answers nothing until it has made the program it was handed, so the frame, and with it every press, waited 130 to 175 ms for each heavy world. `frame()` now leaves `chipWait` out before the start card is left and while `preloadBusy()`. The pictures may hitch for a moment then; the page does not. Over 400 frames with preloading going on, frames that took over 12 ms went from 19 (the worst 175 ms) to 2 (24 and 14 ms). Nothing is made ahead of need in the first `PRE_WAIT` (2.5 s). `MF.boot` lists each file's start-up time, slowest first, and `MF.bootAt` when the app was ready, for looking at this again.

**Before the app has loaded.** `index.html` has a `modulepreload` line for every file in `js/` (`tools/unit.mjs` fails if one is missing or names a file that is not there), so the browser fetches them together instead of after `main.js` has arrived. A press on a start card button before the app is ready is kept by a few lines of script in the page (`window.mfEarly`; the button says "Starting"), and `loop.init` answers it. Not measured: any of this on a phone, on Windows (where making a program takes far longer), or over a real network.

- Without `KHR_parallel_shader_compile` nothing is made ahead, because there is no way to do it without stopping the pictures. Everything is then made when first chosen, as before. Chrome and Edge have it; software rendering in headless Chrome does not, so `tools/check.py` runs the old path.
- Some chips stop drawing while they make a program even with it. If two gaps of over 0.25 s between pictures are seen while a program is being made after the start card has been left, `preSlow` is set and nothing more is started for the rest of the visit.
- Nothing is started during Hold still or a recording.
- `localStorage["mirrorfold-preload"]` is set while this is going on and removed when it ends or on `pagehide`. Found at start-up, it means the last visit ended in the middle, and making things ahead is left out for that one visit.
- Tested on one desktop chip through `--use-angle=gl`: all 24 programs in about 2 s with no gap over 0.1 s, and choosing lands and worlds while they were still being made gave no error. Not tested on a phone.

### Dither

The scene shader, the land shaders and `FS_FINAL` each end by adding a fixed grain of half a step of brightness (interleaved gradient noise from `gl_FragCoord`, between -0.5/255 and 0.5/255). Every picture in the pipeline is 8 bits a channel, and without it a smooth dark gradient (fog, a cloud world, the inside of the Mandelbrot set) is written as visible bands. The grain does not change from frame to frame, so it does not flicker and does not disturb Hold still.

### Resolution and the frame-time governor

`resize()` sets the drawing buffer to `cssSize * min(devicePixelRatio, cap) * q`.

| Detail mode | `q` | DPR cap | Adaptive |
|---|---|---|---|
| auto (default) | starts 0.85, range 0.6–1 | 2 | yes |
| sharp | 1 | 3 | no |
| fast | 0.5 | 2 | no |

In auto mode, every 30 frames the mean frame time is checked: above 36 ms, `q` is multiplied by 0.9; below 22 ms, by 1.06. When to step is decided by `detailNext` and what changes by `detailStep` (both pure functions, tested in `tools/unit.mjs`). A step down takes two slow readings in a row, since one is often the page doing something else. After a step down nothing goes up for 20 s; if that step down undid a step up, the wait doubles, up to 160 s, so a chip near the edge is not shaken back and forth (each change rebuilds every picture, which shows as a hitch). With the land on there is a second number, `landQ` (1, 0.7 or 0.5): the size of the land's own picture beside the whole picture. `landLayer()` makes `tL` that size, `landPass` takes its resolution from the picture it is given, and the land alone is drawn into `tL` and copied up to `tA` when `landQ` is below 1. Going down, `q` goes to 0.6, then `landQ` to 0.7 and 0.5, then `q` on to 0.35; going up, `q` first, and `landQ` only when the mean frame time is under 12 ms. The reason: the land costs about three times a world per pixel (measured in software rendering, 61 ms against 23 ms), and a user's Intel laptop chip took 60 to 75 ms a picture for land over a world at `q` 0.35. Whether this is enough there is not yet known. No single part of the land shader stood out when the shadow, the mirrored pass and the step count were each cut in turn, though the timings were too noisy to rule much out. The policy is to give up frame rate before sharpness. An earlier version started at 0.55 and dropped to 0.3, which users found too blurry.

**Kept between visits.** Each change auto makes is written to `localStorage["mirrorfold-detail"]` as `{q, landQ}` and read back at start-up through `detailSaved`, which ignores anything out of range. Choosing Detail auto again starts it afresh at 0.85.

**A visit that ended while starting.** `localStorage["mirrorfold-load"]` is set at start-up and removed after 600 frames or on `pagehide`. If it is still there at the next start-up, the last visit ended before the pictures were running (most likely the graphics chip or the tab gave up), so `detailLower` takes `q` to 0.7 of what it was (at most 0.6, at least 0.35) and `landQ` to 0.5, and a message says so. Losing the graphics context does the same for the next visit. Auto climbs back if the device can take it. Not tested on a device that really runs out; a page killed by hand in headless Chrome was.

March steps are fixed at compile time: `STEPS` is 96 on touch devices and 120 otherwise; volumetric `VSTEPS` is 44 and 56.

## 5. The scene shader

`fragSource(w)` assembles: a header of `#define`s and uniforms, the world's own GLSL (`w.glsl`, which defines `float map(vec3 p)` or `float dens(vec3 p)`), then a shared `main`.

### Ray setup

```glsl
vec2 uv = (2.0*gl_FragCoord.xy - uRes) / sqrt(uRes.x*uRes.y);
```

Dividing by the geometric mean of width and height keeps the field of view sensible in both portrait and landscape. The ray is `rd = normalize(uCam * vec3(uv, uFov))`, where `uCam` is a 3x3 matrix whose columns are the camera's right, up and forward vectors and `uFov` is nominally 1.15 (smaller is wider). `uFov` narrows the lens slightly with speed, bass and boost.

### Kaleidoscope mirrors

Applied to `uv` before the ray is built, when `uSeg > 0`:

```glsl
float seg = 2.0*PI / uSeg;
float a = mod(atan(uv.y, uv.x) + uSpin, seg);
a = abs(a - 0.5*seg);
uv = length(uv) * vec2(cos(a), sin(a));
```

The angle is folded into one wedge and mirrored about the wedge's centre line, so the image is continuous across every seam. Because the fold is on the ray direction, not the screen image, the result is a true kaleidoscope view of a 3D scene. `uSpin` rotates the wedges slowly.

### Sphere tracing

```glsl
float t = 0.002;
for (int i = 0; i < STEPS; i++) {
  d = map(ro + rd*t);
  if (d < 0.45*uPix*t) { hit = 1.0; break; }
  if (t > MAXD) break;
  t += d;
}
```

`uPix = 2 / (sqrt(w*h) * 1.15)` is the angular size of one pixel, so the hit threshold is 0.45 of a pixel's footprint at distance `t`. This ties level of detail to screen resolution: fractal detail finer than a pixel is not resolved, which removes most aliasing speckle. The normal is a four-tap tetrahedral gradient with epsilon `0.8*uPix*t`.

### Shading

- `orb` is a `vec4` orbit trap that each world's `map` fills: typically the minimum over iterations of `(abs(p), dot(p,p))`. It supplies colour variation.
- Base colour: `pal(uHue + 0.8*orb.w + 0.25*orb.x)`, mixed toward a second palette lookup by `orb.z`.
- Lighting: one directional light fixed relative to the camera (`uCam * (-0.5, 0.7, -0.5)`, normalised), a head-light term `nd*nd` where `nd = |dot(n, rd)|`, and a specular highlight (power 28).
- Ambient occlusion is derived from step count: `ao = (1 - steps/STEPS)^1.5`. It is free and looks good in crevices.
- Animated bands: `smoothstep(0.75, 1, 0.5 + 0.5*sin(24*orb.w - 1.2*uTime))`, brightened by the mid band.
- **Surface grain** (`uSurf` 1, the Surface chooser, `SURFACES` in `state.js`, `sel.si`): the base colour is not one palette colour to a part of a shape but a wood grain worked out from the place the ray lands, coloured `pal(uHue + 0.12*orb.w + 0.5*dark) * (1 - 0.5*dark)`, so each ring runs through half the palette and ends in a darker line (the palette Wood is browns, which gives timber). The grain is `woodAt` in `js/shaders.js`. The place is turned into angles `q = p * 2*pi*n / period` (`uPer`, the world's period this frame; `n` the whole number nearest half the period, so a trunk runs along z about every 2 units), and the grain is built only from sines and cosines of whole multiples of `q`, so it repeats exactly where the world does and does not jump when the camera is wrapped. Rings: `fract(10*sqrt(2.02 - cos qx' - cos qy') + wobble)`, cubed, so each year darkens to a line. Rings finer than a pixel fade to their average (`sharp`). Three more samples tilt the normal so the dark lines stand proud; fine fibres (three sets of waves across the trunk) show close to. The rings' waves drift with the clock (`uTime`), grow with the middle band's pulse (`uMid`), and the rings step a third of a ring on the beat (`uBeat`); those reach the shader as uniforms, so both eyes of the VR viewer see the same, and Hold still, which gives the scene no clock and no sound, sees them stand still. On the grain the glowing bands, the rim light and the highlight are turned down. Journey can change it (the `surface` entry of a template: a name from `SURFACES`; off means plain), behind a transition as mirrors are. Not in share spots or a pack's scene yet.
- **The other surfaces** (`uSurf` 2 to 7, same chooser; all in `js/shaders.js` beside the grain, all in the palette's colours, all taking the sound only as the uniforms `uBeat`, `uMid`, `uHi`, so Hold still and the VR viewer are safe as for the grain). Four are made of blocks: `sfN(k)` gives a whole number of blocks to the world's period on each axis at about `k` to a unit, the place in blocks is `p*sfN/uPer + 0.37` (the 0.37 keeps faces that lie on simple fractions of the period, as Sponge's do, off the joints), and a block's chance number is taken from its count round the period (`mod(c + 0.5, sfN)`), so the pattern repeats where the world does. **Dots** (2): balls on two grids, one in the gaps of the other, 6 blocks to a unit, radius `0.25 + 0.12*uBeat` of a block; a surface cutting one shows a dot in the opposite palette colour, the outer 0.07 of a block of it a dark border. **Tiles** (3): 3 blocks to a unit, each its own shade, dark joints within 0.03 of a block's side, not counting an axis the surface faces (`|n| > 0.7`); a tile gives off light when its own slow wave is high, scaled by `0.12 + 1.2*uHi`. **Marble** (4): the grain's angles `q`; a vein where `sin(3qx + qz + (2.2 + 1.5*uMid)*turb)` crosses zero, `turb` three sines of whole multiples drifting with the clock, the vein's sharpness `6 - 3.5*uBeat`. **Wire** (5): 5 blocks to a unit, the surface darkened to a tenth, the joints (width `0.03 + 0.03*uMid`) giving off light with a wave running along them, times `0.7 + uBeat`. **Cells** (6): a point by chance in each of 3 blocks to a unit, 27 blocks searched; colour by the nearest point, a dark edge where the two nearest are within `0.03 + 0.06*uBeat` of each other. **Pearl** (7): no place at all; the palette is looked up by `1.3*(1 - |n.rd|) + 0.5*n.(fixed direction) + 0.3*uMid`, and the highlight is 2.2 times stronger. Each fades its fine detail by the pixel's footprint `uPix*t`. All of them turn the glowing bands down or off. None has been seen with sound playing, or on a real chip. **Chrome** (`uSurf` 8) is different in kind: inside `#ifdef CHROME` it follows a second ray from the hit, the way a mirror would send it, for `RSTEPS` steps (40, or 28 on a touch device), and shows what that ray meets (the shape's own orbit-trap colours, darkened by how many steps the ray took and faded by distance; no normal is worked out for it) as light given off by a dark surface. That is two more copies of `map` in every program, so it is compiled in only while chrome is chosen: `fragSource` reads `chrome` (`setChrome`), and the programs made with it are a set of their own (see Packing, *Sets of programs*). A pack world's program never has it, so there chrome looks like plain.
- **Ribbed** (`uSurf` 9, after chrome's 8): ridges from `sin` of `24 q.z + 8 q.x + 8 q.y` pushed about by two slower sines of the same angles `q`, so it repeats with the world as the rule requires; the surface is tilted by the ridges' slope (worked out, not sampled), the colour is 60% taken out, and the highlight is turned up. Ridges finer than a pixel fade to their average. It came with the Biomech world, as did the **Airbrush** filter (`fx` 16 in `FS_FINAL`: brightness with more contrast, tinted cool to warm, a tenth of the colour kept) and three palettes.
- Fresnel rim, exponential fog (`exp(-FOG*t)`, `FOG` per world), a step-count glow, vignette.
- Tone map `col/(1+0.2*col)` after an exposure of 1.35, saturation 1.4, a full smoothstep S-curve, `pow(col, 1.15)`, then gamma 1/2.2.

### Orb

A glowing sphere drawn analytically after the march. `uOrb` is `(position, radius)`; radius 0 means off. The closest approach of the ray to the orb centre is found in closed form; the orb is visible only if that point is in front of the camera and nearer than the surface hit (`tmax`). It draws a hard core plus two Gaussian halos.

### Volumetric worlds

When `w.volume` is true the shader takes a different branch: a fixed-step march accumulating `pal(...) * VMAP(dens(p))` with a per-step falloff of 0.93 and a start that is a different part of one step in for each pixel (interleaved gradient noise over the whole of `VSTEP`, with a little plain hash noise added, because the even pattern alone showed as diagonal hatching round the Nebula's stars), so the steps show as fine grain and not as layers. Hold still moves the pixel's position, so the grain averages away. `VMAP` and `VSTEP` are `#define`d by the world.

### The thrown light

`js/flits.js`. **Sprites**: `NFLIT` (8) small dots of light that wander through the world on paths of their own. `stepFlits`, a step of `frame()` after the thrown light's, moves them and fills `flitU` (place and size of each, size 0 for none) and `flitA` (how strongly each shows), which `drawScene` gives the scene shader as `uFl` and `uFlA`. Sizes and margins are in units of the open space round the camera, `s` = its distance to the nearest surface held between 0.01 and 0.6, so they look and behave alike in a tight world and an open one. A sprite arrives at a place by chance 3 to 9 `s` ahead of the camera and inside the view (`flitAim`), if that place is at least `0.3 s` in the open, with a heading by chance. From then on it is not tied to the camera: `flitMove` moves it. Its heading is turned a little every frame by a push that itself drifts by chance (the wander); every 3 to 9 seconds it zigs, taking a new heading mostly sideways to the old one with a burst of speed (up to 2.5 times) that dies away in about a second. It keeps clear of surfaces: where it is, and `0.35 s` ahead along its heading, a surface nearer than `0.35 s` turns the heading away along the surface's direction (`facing` from `spark.js`, six calls of `de`), harder the nearer it is; nearer than twice its size it is put back out and the part of its heading that points in is taken away (`flitSlide`); and it never moves further in a frame than half the distance to the nearest surface. Its speed is 0.6 of what the camera could fly at where the sprite is (`min(world speed, 2.6 * distance)`), so the camera overtakes it. It lives 10 to 25 s, fading in over `FLIT_IN` and out over `FLIT_OUT` (`flitFade`); more than `2 s` behind the camera or 20 `s` away it starts to leave at once; then it waits up to 2.5 s and arrives again ahead. Its size is `0.07 s`, up to 1.7 times that on the beat. The shader's `flit()` draws a disc with a faint halo in the palette's own colour (`pal(uHue + hue)`, a different `hue` for each sprite, no white mixed in, so they follow the palette as it changes and drifts), only if the dot is nearer than the surface hit: so walls hide them, the kaleidoscope mirrors them, and the VR viewer gives each eye its own view. The shader names the eight by fixed numbers (no picking from a uniform list by a number worked out as it runs); a unit test holds the count equal to `NFLIT`. They do not move while Hold still is on, and do not swell then either. None in a pack world (it asks `de` every frame), a zoom world, the land alone or the video alone. The Sprites button is remembered in `localStorage["mirrorfold-sprites"]`; with reduced motion asked for it starts off. `render.py` and `thumbs.py` switch them off so that pictures stay comparable. Tested by `tools/unit.mjs`, which flies a sprite for twenty seconds from open places in six worlds and fails if it is ever within its own size of a surface or stops moving (over every solid world, 40 seconds each, the nearest any came was about 1.8 sizes). Not tested: a real chip, the VR viewer, and how the flight looks (the headless frame loop stops after about six frames).

Each sprite has a role (`FLIT_ROLE`). Two wander as above. Three are a **flock**: sprite `FLIT_LEAD` wanders and the two followers (role 1) come in beside it (`arriveBy`), stay as long as it does, and each frame before their ordinary step are turned by `flitFollow`: toward the leader when more than five sizes from it and away when nearer, away from the other follower inside three sizes, and round toward the leader's heading; they go up to 1.8 times as fast when behind (`pace`), take up the leader's burst, and do not zig by themselves. The ordinary step still keeps them off the surfaces. Three **settle** (role 2, `flitPerch`): within four times the open space of a surface one turns toward it (against `facing`) and flies in, never moving nearer than 2.2 sizes; there it sits (`perch` 1), kept at that distance as the morph moves the surface; when the camera comes within three times the open space it leaves along the surface's direction and away from the camera with a burst, and is a wanderer for the rest of its 20 to 40 seconds. `tools/unit.mjs` flies a flock for thirty seconds and settles and scatters a sprite in three worlds. How any of it looks in flight has not been seen.

`js/spark.js`. **Throw a light** (key G) sets `sparkAsk`; `sparkFrame` throws on the next frame, when the distance to the nearest surface is known. `throwSpark` starts the ball just ahead of the camera with the camera's velocity plus 1.6 times the speed the camera could fly at here, and a radius of a twentieth of the distance to the nearest surface (between 0.0015 and 0.03). `stepSpark` moves it; when `de` at its centre is less than its radius it is pushed back out along the surface's direction (`facing`: central differences of `de`, six calls) and its velocity is reflected and multiplied by `SPARK_KEEP`, 0.8 (`bounce`). It is wrapped by the world's period, drawn at its nearest copy, and shrinks over the last three of its `SPARK_LIFE` 20 seconds. It does not move while Hold still is on. The scene shader draws it with the same `ball()` function as the orb, from `uSpark`, in another palette colour. Because it asks `de` every frame it is refused in a pack world; a cloud world has nothing to bounce off; the land alone and the video filling the screen have no world. Measured in headless Chrome over 900 frames in Sponge, Julia and Box: 8, 1 and 6 bounces, never deeper into a surface than a tenth of its radius at the end of a step.

## 6. Worlds

### Data shape

```js
{ id: "lattice", name: "Lattice",
  hue: 0,            // offset added to the palette phase
  fog: .18,          // fog density
  maxd: 16,          // far limit of the march
  speed: .55,        // top flight speed
  start: [.8,.45,.1],// camera start, or null to sample for open space
  period: function(m){ return [2,2,2] },  // repeat period per axis; may depend on the morph value m
  glsl: [ ...lines defining float map(vec3 p) and filling orb... ],
  de: function(x,y,z,m){ ... },           // the same distance estimator in JavaScript
  volume: true }     // only on volumetric worlds, which define dens() instead of map()
```

Two requirements matter more than anything else when adding or changing a world:

1. **`de` must mirror `map`.** JavaScript evaluates the same distance field to scale flight speed, steer the journey autopilot and place orbs. If the two drift apart the camera will clip through walls or crawl in open space.
2. **The field must be exactly periodic with `period`.** Each frame the camera position is wrapped into one period (`pos -= per * floor(pos/per + 0.5)`) to keep `float` precision. If the field is not periodic at that interval the wrap is visible as a jump.

`uM` (GLSL) and `m` (JS) are the morph value, `sin(0.09*T) + 0.15*sin(0.31*T)`, roughly in [-1.15, 1.15], where `T` is morph time. Each world maps it onto one of its parameters.

### Shared building blocks

- **Mirror tiling.** `p = abs(mod(p + P/2, 2P) - P) - P/2` reflects space into a cell of width `P` centred on the origin. It makes any bounded fractal endless with period `2P`, and, unlike plain `mod`, keeps the distance field continuous and exact: the nearest surface to a point is always in its own cell, because a mirror image is never closer than the original. JS helper: `tile(x, P)`. The eight worlds that are one bounded shape repeated (`packs: true`) do not call it themselves: they call `pkP`, which is this tiling in the packing Grid and something else in the others (next section).
- **Triangle-wave fold.** `p = abs(mod(p + c, 4c) - 2c) - c` equals a box fold `clamp(p,-c,c)*2 - p` (up to sign) near the origin but is periodic with period `4c`. It turns clamp-fold fractals, which are bounded, into endless ones.
- **Sphere inversion.** `k = s / dot(p,p); p *= k; scale *= k`, optionally clamped. The running `scale` is the derivative used to turn the final primitive distance into a world-space distance.
- **KIFS folds.** `p = abs(p)` plus conditional swizzle swaps reflect space into a fundamental domain before a scale-and-offset step.

| Nebula | Volumetric Kaliset | `p = abs(p)/dot(p,p) - f`, 10 iterations, accumulating `|len - prevLen|`; cubed | 2 | `f = 0.55 + 0.03m` |
| Aurora | Volumetric warped gyroid | Three octaves of `p += A*sin(p.yzx*F + t)`, then `exp(-k*|gyroid|)` ribbons | 2π | ribbon width |
| Lanterns | Volumetric lights | One soft light to a unit cell and one to a half cell, each off its cell's middle by a hash of the cell (mod 8) and swaying with the clock, faded toward the cell's sides so that none is cut; plus a faint gyroid haze | 8 | size of the larger lights |

Safety factors (0.42, 0.6, 0.8 and so on) are there because some of these estimators are not strictly 1-Lipschitz: twists, sums of gyroids and clamped sphere folds can overestimate distance. Lowering a factor trades speed for fewer overshoot artifacts.

Tangle's cell number is worked out with whole numbers below 2^24 and `floor(mod(x + 0.5, y))`, never a `fract(sin())` hash: the chip and JavaScript must agree on every cell, and a chip's `mod` may be off by a hair at an exact multiple. Kleinian's estimator never reports more than 0.09, so flight there is slow and even.

Octave multipliers in Coral are integers (3, 9) so the sum stays periodic at 2π. The Gates twist rate is `2π/16` so the field repeats exactly every 16 units of z.

### Packing

`js/packing.js`. Eight worlds are one bounded shape repeated: Citadel, Bulbs, Shards, Crystal, Julia, Hive, Mandelbrot, Pyrite (`packs: true`). How the copies are set out is the packing (`packing`, an index into `PACKINGS`; chosen with the Packing button, kept in `localStorage["mirrorfold-packing"]`, set only through `setPacking` in `js/choose.js`).

- **Grid** (0) is the mirror tiling above, unchanged: period `2P`.
- **Scattered** (1) cuts space into boxes of width `P` and puts one copy in each.
- **Nested** (2) starts from boxes of width `2P`. A box is left whole or cut into eight (`PK_SPLIT0` of 251), and each of those eight is left whole or cut again (`PK_SPLIT1`), so the boxes are `2P`, `P` and `P/2` wide.
- **Sponge** (3) has no chance in where things go. Blocks of three boxes of width `3P` each way: the middle one holds one large copy, the six at the middles of the faces are empty, and each of the other twenty is cut into 27 boxes of width `P`, of which the same seven are empty and twenty hold a copy. The empty boxes line up into square holes that run right through. Period `9P`. Copies are turned by chance but not moved off the middle.
- **Helix** (4), **Shells** (5) and **Descent** (6) are not made of boxes. See *Balls* below.

In all three, a copy is sized so that the ball of radius `R` that holds the shape (measured for each world over the whole morph, and passed to `pkP`) is `PK_FILL` of half its box; it is moved off the middle of the box by a chance amount on each axis, as far as the room allows while leaving `PK_GAP * P` clear at the walls; it is turned by two chance angles; and about one box in eight is empty (`PK_EMPTY`). The largest boxes do not line up: each layer of them is slid along y, and each row within a layer along x, by a chance amount, so no flat lane is left in those two directions, and the lane between layers is only twice the gap thick.

**Chance numbers.** Everything a box gets comes from `pkh` and a chain of six more numbers, each 0 to 250, made from the box's whole-number place counted round the period (`pkm`, which is Tangle's `mo`). Every product stays under 2^17, so the chip's 32-bit numbers and JavaScript's doubles agree exactly. The period is `PK_N` (4) of the largest boxes: `8P`, where the grid's is `2P`. `pkPer(P)` gives it, and those worlds' `period` calls it, so the period changes with the packing. `pkMul(w)` is how many times longer than the grid's it is, for things sized from the period (the orb).

**The distance in the boxes.** `pkP(p, P, R3)` (the three kinds' radii) finds the box (`pkB`), and returns the place within its copy: moved, turned, and divided by the copy's size `pkS`. The world then works out its shape as before and ends with `pkD(d)`, which multiplies by `pkS`. Three things keep it right and cheap:

- *Nothing leaves its box.* The answer is never more than the distance to the box's nearest wall plus the gap (`pkW`), because that is the least the distance to anything in another box can be.
- *Far from the copy the shape is not worked out.* Beyond `PK_FAR` (1.5) times `R` from its middle the distance is taken to the ball that holds it, and `pkP` sets `pkO` to the finished answer; the world's `map` returns it at once. The worlds' own estimates were only ever used within about that range, and some go wrong beyond it. In an empty box the answer is the wall limit alone.
- *Open space looks across one wall.* Where that finished answer would be held back by the wall, `pkP` looks up the one box across the nearest wall and takes instead the least of: the ball that holds that box's copy, and the gap plus the distance to the nearest of this box's next wall, that box's sides and that box's far end. A ray running along a wall then takes long steps. (Before this, such rays took a hundred short ones and showed as lines across the picture, through the step-count glow and shading.)

**JavaScript's half** uses the same numbers and gives the same answer as the shader when `pkPlain` is set, which is how `tools/probe.py` compares them, once in each packing and again with the shapes mixed and the pulse a wave (one point in a run may differ there: a point on the line where the shape stops being worked out can fall either side of it). Otherwise, where the wall would hold the answer back, it looks in all the boxes within half a grid step (`pkWide`, 27 places, which finds them all because no box is narrower than that) and returns the nearest ball, or half a grid step if none is nearer. That is the open space as it is, which flight speed, the autopilot, the sprites and the orb need: the shader's limit would read as a wall where there is none. So for these worlds `de` is not the same number as `map` in open space: it is never less, and they agree wherever either is near a surface.

**Balls.** The last three packings give each copy a ball and find, for a place, the copy whose middle is nearest among a few that could be (`pkHx`, `pkCg`; `helix`, `cage` in JavaScript). The distance is that copy's shape, held to the nearest of: the next nearest ball, the copies not looked at, and what lies across the block's wall. Those are true distances to things, not walls, so JavaScript uses the same answer and `pkPlain` changes nothing.

- *Helix.* Blocks `HX_W` (4) `P` wide in x and y, each with two strands opposite each other round the z axis: a copy every `HX_H` (0.5) `P` of height, `HX_N` (6) to a turn, its middle `HX_R` (1.25) `P` from the axis in a ball of `HX_B` (0.5) `P`, turned to face outward. The five copies of each strand nearest in height are looked at; any other is at least `2.5 HX_H - HX_B` away. Period `4P, 4P, 3P`.
- *A cage* is twenty balls of radius `CG_B` (0.4) on the corners and edge middles of a cube two across, in the cage's own size `s`. All of it lies between 1.014 and 2.132 from the centre, so a cage a third the size (0.338 to 0.711) fits inside with room between. A place's cage is the one with `s = P * 3^k`, `k = floor(log3(r / (CG_CUT * P)))`; the nearest ball's middle is the corner in the place's octant, or the edge middle got by setting the smallest coordinate to nothing if that is under a half. The answer is held to `max(dc, 1 - dc) - CG_B` (no two middles are nearer than 1), `r - CG_IN` (the cage inside) and `CG_OUT - r` (the cage outside).
- *Shells* repeats that nest every `SH_W` (3.2) `P`, with a largest cage (`k` no more than 0) and each cage turned `SH_TW` about z from the one outside it. Period `3.2P`.
- *Descent* is one nest with no largest cage and no turn, so the field at `3p` is three times the field at `p`, exactly (`Math.pow(3, k)` in JavaScript). The world is not periodic; its `period` is `12P` only so that the camera's wrap never acts. `move` calls `pkJump`, which multiplies the camera's place by 3 when it comes within `DP_IN` (1.5) `P` of the centre and by 1/3 at three times that, and scales the velocity; `fr.jump` carries the factor, and the orb, the sprites and the thrown light are moved by it in the same frame. Lengths in the scene shader that do not come from the world are multiplied by `SC` (`uPkZ`, which `worldPass` sets to `pkZoom`: 1 at the near end of the camera's range, 3 at the far end): the first step, the reach `MAXD`, the fog, the normal's offset. `measure` multiplies the top speed by the same. A surface's pattern is worked out from `SP`, the place within the copy (`pkQ`), so it grows and shrinks with its copy. With those, the picture at the two ends of the range differed by a mean of 0.3 in 255 in headless Chrome, against 21 for a place a quarter of the way between. `placeCam` starts the camera between two cages looking in along one of the six ways through, and the autopilot leans toward the centre. Not done: a doorway there (`doorMay` refuses), a recorded flight (`flightRecStart` refuses, and a recording ends if the descent begins; its curve between samples would cut across a move), and friends' places, which are right only up to a factor of three.

**The pulse** (`pkWave`; Pulse button, `localStorage["mirrorfold-pulse"]`). Each copy has a lag `pkF` in seconds: `pkLag` of where its box is in the period (three sines, 0 to `2 PK_LAG` = 35 s), along the helix by its angle, in a cage by which ball it is, and in the shells `SH_LAG` more for each cage inward. With the wave on, the copy's morph is the morph that many seconds of the morph's clock ago. The morph is two sines of the clock, so `loop.js` hands the clock to `pkTick` each frame, which keeps the sine and cosine of each; they go to the shader as `uMw`, and `pkMo` works the lagged morph out the same way in both halves. Inside a shape `uM` is `#define`d to `pkU`, that copy's morph; JavaScript's `sde` is handed it. Off, `pkU` is `uM`. It follows the morph's clock, so a guest and a played flight show the same shapes. The grid has neither this nor mixing: its copies join across the cell walls, and two neighbours at different morphs or of different kinds would not meet.

**Mixed shapes** (`pkMix`; Shapes button, `localStorage["mirrorfold-shapes"]`). Each packed world gives its shape alone (`shape`, `sde`, `rad`) and names two others (`mix`). `packSrc` writes the world's GLSL: its shape as `sh0`, the other two as `sh1` and `sh2` when mixed, and a `map` that asks `pkP` for the place and the kind `pkK`. `packDe` does the same in JavaScript. The kind is by chance in the boxes (the largest boxes of nested and sponge keep the world's own), by position along the helix, and by corner or edge in a cage. Each kind is sized by its own radius.

**Sets of programs.** Mixed shapes and chrome both change what `fragSource` returns, and both make a program larger, so neither is compiled unless chosen. `setProgSet(key, WORLDS)` puts each built-in world's `prog`, `U`, `job` and `probe` away under the old key and brings out the new key's, if made; the key is `"m"` for mixed and `"c"` for chrome, together or alone. `progSync` in `js/choose.js` is the only caller, and builds the world in use at once; the others are built when chosen, as at the start (the preloader does not go back over them).

**What carries it.** Changing the packing moves every shape, so `setPacking` puts the camera in open space again (`placeCam`) and `requestPacking` does it behind a transition. It is a Journey category (`packing`, left as set by default), one of the kinds a recorded flight notes (`FL_KINDS`) and a host sends to guests (`TG_KINDS`, `pk`), part of what Hold still compares, and in a share spot's second character. A doorway is closed if the packing changes while it stands, and both of its passes get the same `uPk`. The pulse and the shapes are carried the same ways, as Journey categories `pulse` (`together`, `wave`) and `shapes` (`one kind`, `mixed`), and in the share spot's seventeenth letter.

### Adding a world: checklist

1. Add an entry to `WORLDS` with `glsl` and a matching `de`.
2. Fill `orb` in `map` (start it at `vec4(1000.0)`, take a `min` each iteration, keep `orb.w` roughly in 0..1).
3. Give an exact `period`. If the fractal is bounded, mirror-tile it; or, to have it take the packings, measure the radius of the ball that holds it over the whole morph and follow the eight worlds that give `shape`, `sde`, `rad`, `grid` and `mix`.
4. Pick `start` in open space, or use `null` to have 300 random points sampled for the largest distance.
5. Add the id to any built-in template sets that should include it (templates with `set: null` include everything automatically).
6. Update the world count in the start card text.
7. Run `python3 tools/render.py --world <id> -o x.png`, try two or three palettes, then `python3 tools/check.py` and `python3 tools/probe.py`.
8. Run `python3 tools/thumbs.py world-<id>` for its picture in the chooser (`tools/unit.mjs` fails without it), and `python3 tools/render.py --all -o docs/worlds.jpg`.

Worlds were developed by writing several candidates at once, rendering them, and keeping the good ones. First attempts often needed one retune (Crystal collapsed to dust until its rotation was reduced; Nebula and Aurora needed their gain changed by an order of magnitude).

### Inside out

`inOut`, `inShell(w)` and `inDe` in `js/worlds.js`; `setInside` in `js/choose.js`. Open space and solid swapped. A fractal's distance estimate is only good outside its shapes (inside, it is nothing, or for Julia a large negative number that means nothing), so the complement cannot be taken at the surface. It is taken a shell's width out: the new distance is `(c - max(d, 0)) * IN_STEP`, where `d` is the world's own distance and `c` the shell, so the new walls are the surface `d = c`, and everything nearer the old shapes, the shapes included, is open. `IN_STEP` (0.8) is there because far from the shapes an estimate may grow faster than the true distance, and the swapped one would then overstep. `c` is `IN_PART` (0.3) of the largest `d` on a fixed 7 by 7 by 7 grid of places in one period at morph 0, worked out once for each world and packing and kept (`inKept`): a fixed grid and not chance places, so that every device gets the same shell, which Fly together and share links need.

In the shader `fragSource` renames the world's `map` to `map0` with a `#define` and adds a `map` that makes the swap when `uInv` (the shell) is above 0. In JavaScript `init()` in `js/worlds.js` keeps each world's `de` as `de0` and replaces `de` with one that answers through `inDe`, so flight, the autopilot, doorways, sprites, orbs and the rest need no change. Two differences from the shader, both deliberate: inside the new walls `inDe` answers 0, not a negative number, because much of the flight code takes the size of a distance for open room and would fly into the wall and speed up; and `tools/probe.py`, which runs every world once more inside out, counts a negative answer from the chip as 0 for that reason. The autopilot's four feelers reach only a third of a shell to twice the room (`autopilot`), since the open space is a layer about a shell thick and the usual reach lands in the walls on both sides. In the shading the world's colour measures are folded into -1 to 1 (`tr/(1+abs(tr))`) while `uInv` is on: away from the shapes they run to large numbers, and the colours came out as rings too fine to see.

It is a Journey category (`inside`, keep by default), one of `FL_KINDS` and `TG_KINDS`, and the eighteenth letter of a share spot. Off in the descent (whose distances grow with the camera's, so one shell would not do), and in cloud, zoom and pack worlds. Tested: `tools/unit.mjs` against a made-up world; `tools/probe.py` (shader and script agree in all 22 worlds with surfaces); stills of ten worlds looked at; thirty simulated seconds of Journey inside out in Julia, Temple, Sponge and Bulbs kept clear of the walls (before the two differences above it spent most of its time inside them); a loop flown inside out with shafts on came round exactly.

### The Fabric

`js/fabric.js`, the `fabric` entry in `js/worlds.js`, `keepAbove` in `js/camera.js`. A world of another kind: one sheet with sky above it (`sheet: true`), whose shape moves with the clock and the sound, not with the morph.

**The waves.** `fbSet(time, low level, mid level, treble level, beat pulse, calm)`, called by `frame()` after the clocks unless Hold still is on, fills `fb`: five heights and seven angles. A height is its resting value plus what its part of the sound adds (`FB_BASE`, `FB_SND`); an angle is its rate times the time, folded into one turn in doubles so that the chip's 32-bit numbers lose nothing. `fbH(x, z)` adds five waves, every one a sine of whole multiples of `FB_K` = 2 pi / 12, so the cloth repeats every 12: a billow (one wave to the period along x, its front bent by a sine of z), a cross wave (2 by 3 to the period), a flutter (7 to the period, quick), a swell (3 by 2, standing, its height a cosine of time), and a gust (one front to the period, `exp(6(cos - 1))`). The scene shader gets `fb` as `uFb` (declared in the world's own GLSL; set in `worldPass` and in the probe) and works out the same sum, so `map` and `de` agree at every moment; `tools/probe.py` compares them like any world's. `fbSet` has no memory: the same time and sound give the same cloth, so a flown loop comes round, and under Hold still it is not called at all. With reduced motion asked for the waves are half as high and half as fast.

**Flying.** The camera cannot go through. `keepAbove`, a step of `frame()` after everything else that moves the camera, calls `fbHold`: below `fbH + FB_TOP + FB_CLEAR` (the threads' top and 0.12 more) the camera is put there, above `fbH + FB_CEIL` (5) it is put there, and the part of its speed that took it out is dropped. That is needed even with nobody steering, because the cloth rises under the camera as a wave passes. The world does not repeat upward; its period there (16) is a number the camera never reaches, as the descent's is. `turn` eases the horizon level and leaves out the slow roll, as over the land. `autopilot` has a branch for it: it wanders from side to side, holds the view at 0.3 below level, and eases the height to `FB_ALT` (0.9) above the cloth, since over a sheet the usual feelers would only ever say "up". `placeCam` starts the right way up, looking down across the cloth. An orb is put only between the heights in `band`.

**What it does not have.** No doorways (`doorWorld`: one could stand below the cloth) and no inside out (`inShell`). The morph changes nothing. The waves follow this page's own clock and sound, so two people flying together, or a recorded flight played back, see the same weave but not the same waves: a friend's marker can be inside a crest. That breaks the rule that moving geometry comes from the morph's clock or is sent; it is listed under Known weaknesses.

**Tested.** `tools/unit.mjs`: `fbSet` has no memory and holds the sound to 0 to 1; the cloth and its distance repeat every 12; a place put back by `fbHold` is clear of the threads at 400 moments of loud waves; a ray stepped by the distance never ends inside a thread. `tools/probe.py`: shader and script agree. In the page, a minute of autopilot at sixty steps a second with loud made-up sound, begun upside down: it came level, kept 0.47 to 1.06 above the cloth, and was never nearer a thread than 0.17. Stills looked at. Not seen: any of it moving, with real music, or on a real chip; a loop flown there; the VR viewer; the land over it.

### The light wave

`js/lightwave.js`. `stepLightWave`, a step of `frame()`, keeps up to `LW_N` (3) distances `lwR`. `lwStep` starts one when the beat's pulse `fr.bt` rises past `LW_BEAT` (0.4) and the last start was at least `LW_GAP` (0.8 s) ago, and moves each outward at the limit of sight (`maxd`) per `LW_TIME` (3.2 s). `lwBright` gives each its strength from how far out it is: nothing in the first 3%, full at about a quarter, falling to nothing at the end, so that the band never shows on what is close to the camera, where it would pass in a frame or two and read as a flash. In the shader a hit at distance `t` adds `exp(-x*x)` of light for `x = (t - r)/(0.18 r)`, summed over the three, to the surface's own glow. Under Hold still the distances stand. The world beyond a doorway gets the distances times the doorway's `s`. While a loop is flown the beat is `lapBeat`, which is periodic, so the waves are too. Tested: `lwStep` and `lwBright` in `tools/unit.mjs`; one still with two waves out, looked at. Not judged against music.

### Light shafts

`shafts` and `setShafts` in `js/shaders.js`, `setShaftsOn` and `shaftU` in `js/choose.js`. Compiled into the scene shader only when on (`#define SHAFTS`, the letter `f` in the program set's name). After the surface is shaded, six places along the ray between the camera and the hit (or `uSh.z`, if nearer) are each given a short walk of five steps toward a light direction fixed in the world, keeping the least of `5*d/s` on the way (the usual soft shadow), and the sum, faded by the world's fog, is added as light, most when looking toward the light. The six places start a different part of a step in for each pixel, so the steps show as grain, which the trails and Hold still average. `shaftU` gives the reach from the world's scale. A first version asked only how much room there was toward the light at two distances, with no walk; it gave an even haze and no beams. Looked at in Sponge, Temple, Julia and Halls: clear in Julia and Halls, slight in the two bright enclosed ones. Its cost on a real chip is not known.

### Ribbons

`js/ribbons.js`. `stepRibbons`, a step of `frame()` after `stepTogether`, keeps the camera's last `RB_OWN` (32) places a step apart (`rbAdd`; the step is 14 times the ribbon's width, and the width follows the open space round the camera slowly), and for each friend the last `RB_PEER` (8) places their marker was drawn at here, so a friend's ribbon costs no message. `rbFill` writes them into `uRb` (56 points in all), each at its copy nearest the camera, with a brightness that falls along the ribbon and with age (`RB_LIFE`, 45 seconds); the brightness is negative where the line must stop: at a ribbon's end, and where the next point's nearest copy is another copy of the world (the distance between the two is then not what it was when they were added). In the shader `ribbons()` finds, for each pair of points, the place on the line between them that the ray passes nearest, and adds a core and a halo there if nothing is in front; a line is never thinner than a pixel, and fades out close to the eye. It costs every pixel a loop of 55 short steps while `uRbW` is not 0, and nothing otherwise. The points move out with the camera in the descent (`fr.jump`), are cleared on a change of world or packing, and are not added to or aged under Hold still. Left out of the world beyond a doorway and while a loop is flown.

## 6c. The zoom worlds

`js/zoom.js`. **Mandelbrot zoom** (`mzoom`) and **Julia zoom** (`jzoom`) are entries in `WORLDS` with `flat: true` and no `map`. They are also marked `volume: true`, so that everything that already leaves the cloud worlds alone (the probe, the thrown light, the orb's surface check, Journey in the VR viewer) leaves them alone too. The camera still flies its hidden course through an empty world; nothing shows it. `stepZoom` takes any look that is not exactly nothing as the user holding the picture, and then neither the tour nor Drift moves it. So `turn` in `camera.js` finishes a look once it is below a ten-millionth of a radian: left to die away it took about 50 seconds to reach nothing, and a zoom world that Journey came to from a world the autopilot had been steering in sat without moving for that long.

**The view** is `zm`: the middle `x, y` in doubles, `s` (the distance from the middle to the top of a square picture), the turn `rot`, and the Julia constant `jx, jy`. `stepZoom(fr)` runs after `move`: the look applied this frame (`fr.lx`, `fr.ly`) and the sideways inputs slide the middle, the user's forward input (`fr.uz`, before drift or autopilot is added) zooms, `cam.rollIn` turns. With nothing asked for it zooms in slowly (Drift) or runs `tour` (Journey travelling).

**Drawing.** The shader's numbers are single precision, which runs out a few thousand times in. So each pixel is followed only as its difference `dz` from a reference path (perturbation): `dz' = 2*Z*dz + dz*dz + dc`, with `Z` read from a 1024 by 2 picture of real numbers (`OES_texture_float`) that `zoomUniforms` fills from `refOrbit`, in doubles, whenever the middle moves. Row 0 is the path of the view's middle and row 1 the path from zero; for the Mandelbrot set they are the same. When a pixel's value `Z + dz` is smaller than `dz`, or its row runs out, it carries on against row 1 from the start with `dz` set to the value itself (rebasing), which is what keeps one reference good for the whole picture. `zoomIter` sets the step count from `s`, up to `zoomCap()` (1,024, or 384 on a touch device; the loop's fixed bound is the same number). Colour is the smoothed step count through the palette. Without the float texture `build` throws for these two worlds and `setWorldNow` skips them with a message.

**Targets.** `ZTARGETS` holds twenty Misiurewicz points (found by Newton's method on `f^(k+p)(0) = f^k(0)`; `tools/unit.mjs` checks each still lands on a cycle) and one small copy of the set. The last thirteen were picked from every such point with a preperiod up to 14 and a period up to 4, ranked by how far the pattern turns for each tenfold zoom (the angle of the cycle's multiplier over the log of its size), and then looked at. New targets go at the end of the list, because a share link holds a target by its number. Around a Misiurewicz point the picture repeats at every size, so the tour can go to `ZMIN`-ish depths; each target has `d`, the smallest `s` worth going to, and `per`, roughly how many more steps each tenfold zoom costs, from which `targetDepth` works out how deep a device with fewer steps may go. `fixedPoint(c)` gives the Julia tour's point: the alpha fixed point when it repels by more than 1.045 a step, otherwise the beta one.

**The tour.** `pilotTo` is a pure step: while the target is off the picture or near its edge the view backs out; once it is inside, the middle closes on it three times faster than the view shrinks and snaps onto it exactly, which matters because the reference path must be the target's own. Mandelbrot: target, rest `ZHOLD`, next target (mirrored top to bottom at random). While it is on its way the picture turns at `ZTURN` radians a second. Julia: fixed point, rest, out to the whole set, then the constant eases to the next of `JULIAS` over six seconds.

**Share links.** A zoom world's spot is still 16 letters and digits, so `cleanScene` and the hash pattern are unchanged: palette, mirrors, then `zoomSpot`'s 14: the target's number if the reference point is exactly a target (which restores it exactly, and the two numbers for the middle then hold `ox, oy` instead; the last character says whether it is mirrored, and a link made before that character was used, when a mirrored target had 18 added to its number, still opens), the middle to 4 digits each (about three millionths), `log s`, the turn, and the Julia set's number. `zoomFromSpot` holds a view that is not on a target to `s` of a thousandth or more.

**Staying on the busy part.** `zm.ox, zm.oy` is how far the picture's middle is from the reference point `zm.x, zm.y`, in units of `s`, in the plane's own directions (not the screen's). The shader adds it to each pixel's offset (`uZo`), which costs no digits because it is a small number times `s`; the reference path is still the target's own. Every fourth frame while the tour or Drift is running, `interest()` follows a 12 by 12 grid of points over the visible picture in doubles and weights each by the square of how much its step count differs from its neighbours' (capped at `ISTEP`), and returns the weighted middle. On the tour `centreOn` eases `ox, oy` toward it and holds the target at least a quarter of the way in from every edge. With Drift there is no exact point to keep, so `zm.x, zm.y` itself moves. When the user moves the picture, the offset is folded into `zm.x, zm.y` and set to zero.

**Patterns.** Besides the smoothed step count, the loop keeps three things from the path: `near` and `nearI` (the smallest `|w|^2` and the step it came at), the sum `sa` of `0.5 + 0.5*sin(4*arg w)` (worked out as `2xy(x^2-y^2)/|w|^4`, with no `atan`), and `dr`, the derivative of the value with respect to the pixel's position, already multiplied by `s` so it fits a float at any depth. From `dr` comes the distance to the set in view units, `0.5*|w|*log(|w|^2)/|dr|`, and from that `k`, which fades both patterns out between 0.045 and 0.004 of the view from the set so they never get finer than a pixel. Cells: the fraction `f` between step counts and the sign and angle of the last `w` give a cell and its edges (binary decomposition). Stripes: the path's average of the wave, blended between `n-1` and `n` steps by `f` (stripe average colouring). `uZs` is how much of each to show, `zw.c` and `zw.s`, which ease toward `zw.tc`, `zw.ts` over about a second; `setPattern` (the Pattern button, `zpat`) sets the aim, and when it is 0 the tour sets it with `patternPick` at each new target or Julia set. Inside the set the colour is `pal` of `nearI` with rings of `sqrt(near)`.

**The autopilot does not steer a zoom world.** `autopilot` returns at once for a flat world. Before that it wrote `cam.lookX` every frame, which `stepZoom` took as the user sliding the picture, so the tour never sat exactly on its target and never left it.

**The Julia constant and the sound.** `juliaPush` sets `zm.wx, zm.wy` from the smoothed low level and the morph, at most `JPUSH` with the whole set in view and less by `1/(1 + 2.5*decades)` deeper (and to three tenths under `calm`). Everything that uses the constant uses `jx + wx, jy + wy`. The fixed point moves with it, so the view is moved by the same amount each frame, and stays exactly on it if it was. `fixedPoint` takes the unpushed constant as well, to decide which of the two points and which sign of the square root, so neither flips with the music. It does not run during Hold still.

**Hold still** compares `zoomKey()` as well as the camera, so the picture is sharpened only while the view is not changing.

**A fault this turned up.** The scene shader's `uLandT` was only given a texture unit while the land was over a world; otherwise it stayed at unit 0, which at that point in the frame can hold `tA`, the picture being drawn into. The other worlds got away with it. The zoom shader did not: the draw was refused with `INVALID_OPERATION` and the picture was black. `drawScene` now always points `uLandT` at unit 6, bound to the land's picture or to nothing.

## 6a. The land

The land (`landMode`: 0 off, 1 alone, 2 over the world) is a height field, not a distance field, so it does not use `fragSource`. It has its own shader, put together by `landSrc(k)` from the shared template `LAND_T` and one landscape's pieces, a coarse first pass (the same text up to the `/*sky*/` marker plus `LAND_PRE_MAIN`), its own camera position `lpos` and its own JavaScript height `landH`. It shares the camera's direction (`R`, `Up`, `F`), the field of view, the mirrors (`ray()` in the land shader repeats the fold in the scene shader) and the palette.

- **Landscapes.** `LK` lists them (`landKind` is the index): the Alps, canyon country, a strange planet, a steel ball, a city. The last two are not height fields: their entries have `src` (a whole shader built by `landOwn`, with no coarse pass), `h` (a height used only for steering; the ground is level) and `mirror` (the world is drawn whole so they can mirror last frame's `tA`). The ball is one ray-sphere test. The city walks the ray from block to block (`trace`) and tests the few boxes in each; `cityBlock`, `cityH` and `cityExtra` are the same blocks in JavaScript. For the others, `LAND_T` has gaps marked `@` (`@CONST`, `@SHAPE`, `@EXTRA`, `@SKY`, `@ZONE`, `@SHAPES`, `@GROUND`, `@XCOL`, `@COLS`) which `landSrc` fills from the entry's `gl` object. An entry also has its water level, `hmax` (the height above which an upward ray is sky), `flute` (how much the fine layers are turned down where the shape is a cliff, which stops upright grooves and smears), `shn` (shadow steps), its sun, and `shape` in JavaScript. All landscapes use the same noise sum; they differ in `shape()`, which turns the sum into a height. The canyon's shape is a staircase generated for GLSL and JavaScript from one list, `CANYON_STEPS`. Each landscape's two programs are compiled the first time it is chosen and kept in `pLandK`.
- **Free-standing shapes.** A height cannot describe rock with air under it, so a landscape may define `extra(p)`, a distance to shapes placed at most one to each square of the coarsest noise grid (arches and balanced rocks in the canyon; floating crystals, rings and slabs on the planet). Whether a square has a shape, and the height of the ground under it, is worked out once in JavaScript (`xcell`, `landXTab`) and read by the shader from the texture `uX` and by JavaScript from `xh`. Shapes keep half a unit inside their squares and have a height limit, so away from one `extra` returns a safe distance that never becomes small; an earlier version slowed every ray at every square edge. The march, the coarse pass and the shadow all take the smaller of the land step and this distance; `gX` says which was hit, and `xcol()` colours a shape. The entry's `extra` in JavaScript is the same function, used in `frame()` to push the camera out of a shape. It must match the GLSL except for the surface lumpiness.
- **Height.** A sum of value-noise layers. Each layer is weakened where the layers before it are steep, which carves ridges and gullies, and the sum goes through `shape()` to give flat valley floors and steep peaks. Each layer is the previous one multiplied by the whole-number matrix `[2 -1; 1 2]` (a turn of 26.6 degrees and a scale of 2.236). Because the matrix is whole numbers and the noise repeats every 256 squares, the land repeats exactly every `LPERIOD = 256 / LFREQ` units, and `lpos` is wrapped by that.
- **Noise.** `LTAB` is 65,536 bytes from a fixed generator. The shader reads it from a 256 by 256 texture in which each texel also holds its right, upper and upper-right neighbours, so one read gives the four corners of a noise square. `landHash` reads the same table, so GLSL and JavaScript agree exactly at the corners.
- **Precision.** The shader measures everything from the camera. `landPass` works out, in doubles, where the camera sits in each of the 13 noise layers (`uCi` whole part, `uCf` remainder) and in each grid of things (`uLi`, `uLf`) and two grain patterns (`uDa`, `uDb`). Without this the fine layers shake, because a 32-bit float cannot hold a position hundreds of units from the origin to a ten-thousandth of a unit.
- **Levels of detail.** `terrL` (4 layers) for broad slope, `terrU` (4 layers through `shapeU`, never below the true height, used by the march and the shadow when well clear of the ground), `terrM` (6) for marching, `terrG` (6, also returning an approximate slope), `terrD` (9, plus 4 more that fade in within 1.6 units).
- **Things.** `zone()` gives how much a place is forest, meadow or stony ground from slope, height and noise. `things()` scatters one thing to each square of six grids (two of trees, then bushes, boulders, rocks, scree) and returns its height above the land, which the march adds within 2.2 units. Each thing is kept inside its square, so one table read per grid is enough. `treeh`, `bushh` and `rockh` give the shapes.
- **Marching.** `LAND_PRE` runs at one-eighth size. Each ray is a cone wide enough to cover its block of pixels and stops when the cone first touches the land (raised by the tallest thing near the camera). `pre()` in the main shader takes the nearest of the four coarse results around a pixel as the place to start. A step is 0.42 of the height above the land, which can jump through a cliff, so both passes remember the last point known to be outside and go back to it. Low rays near the camera take short steps so no tree is stepped over.
- **Lakes.** A plane at the landscape's `water` level, coloured by `WSHAL`, `WDEEP`, `WGLOW` and `WFOAM`. The loop in `main` runs twice at most: the view, then the mirrored view from the water with a looser march and no streams or cast shadows.
- **Streams (Alps only).** One to each square of a coarse grid, running straight downhill from a point in the square: white where steep, blue where gentle.
- **Passes.** Alone: `landPass(tA)` replaces pass 1. Over a world: `landPass(tL)` first, with alpha 0 for sky and alpha below 1 for far land; then the world into `tA`, where `uLandOn` makes it skip pixels the land covers; lakes mirror last frame's `tA`. `landFx` then picks the picture the effects work on: 0 lays the land over the world into `tC` (`FS_MIX`); 1 uses the world, and the final pass lays the land on top after the filters (`uLandMix` 1); 2 uses the land, and the final pass shows the world behind it (`uLandMix` 2).
- **Flight.** `lpos` moves along the level part of `F` at a fixed speed and its height eases toward the ground here and ahead plus `landClear`. While the land is on, the horizon is eased level, the slow automatic roll is off, and the travel autopilot steers toward the lower side instead of probing the world's distance field.
- **Limits.** In the VR viewer it is drawn for each eye (section 13, Effects in depth), with the sky in its mirrors and no thinning of far land. Not part of Journey templates. Trees cast no shadows. The canyon's and the planet's patterns were tuned from still renders in headless Chrome only; their frame rate on a phone is unmeasured. Relative cost in software rendering (six views, lower is better): Alps 609, canyon 600, planet 816, city 42, ball 18. An arch's legs run straight down without end, so one standing beside a drop shows a leg hanging down the cliff. `proto/alps.html` is the standalone page it was developed in and is no longer needed by the app.

## 6b. The distance probe and Stats

`probe(w, m, n)` asks the graphics chip for world `w`'s distance at the first `n` (up to 16) points in `probePts`. `probeBuild` makes a program from the world's own shader text up to `main`, with a `main` that evaluates `map` at point number `gl_FragCoord.x`, clamps it to -8..8 and spreads it over three colour bytes; `probe` draws that into a 16 by 1 picture, reads it back and decodes into `probeOut`. It exists for two reasons:

- **Worlds in packs.** A pack may not carry JavaScript, so a pack world has GLSL `map` but no `de`. `cleanWorld` checks it (the rules of `cleanCode`, no clock or sound, loops at most 16 times in all, numbers in range); `packWorld` wraps the code as `wmap(p, m)` inside a `map` that first folds `p` into the period, so the world is exactly periodic whatever the code does, and clamps the result. `packFrame` asks the probe once a frame for the camera and the autopilot's four points (`packD`); if the answer takes over 4 ms on average it asks every third frame. `deMany` batches the one-off searches (a starting place, an orb's place) 16 points to a question. Pack worlds are appended after `NWORLD`, are saved in `localStorage["mirrorfold-library"]` as cleaned source, and while one that is not `reviewed` is showing the flash limiter is on. Untested: any pack world on a phone, and the orb in a pack world.
- **Testing.** `tools/probe.py` compares `map` with `de` at 384 random points for every solid world. All 15 agree within 0.002 units plus 0.3% (32-bit against 64-bit arithmetic). This is the automatic check of the rule that the two must match.

Reading a picture back makes the page wait until the chip has finished everything queued before it, which in practice is the rest of the previous frame. So the time the probe takes is mostly a measure of how far behind the chip is, not of the probe's own work. WebGL 1 has no way to read back without waiting; WebGL 2 does (a pixel buffer and a fence).

**Stats** (`statsOn`, `ST`, `statsShow`) shows, twice a second: pictures a second and the longest gap between two, the script time per picture (measured round `frame()`, less the probe), sharpness and buffer size, the renderer name from `WEBGL_debug_renderer_info`, and the probe at the camera: its wait in milliseconds and the chip's distance beside `de`. A low script time with a long probe wait means the chip is the limit; a high script time means the page's JavaScript is.

## 7. Camera and flight

The camera is three orthonormal vectors `R`, `Up`, `F` (right, up, forward) and a position `pos`. The system is left-handed: `R x Up = F`, with x right, y up, z forward.

- **Look.** Input adds to `lookX` and `lookY`. Each frame a fraction `1 - exp(-14*dt)` of the pending amount is applied as a yaw about `Up` and a pitch about `R` (Rodrigues rotation, `rot(v, axis, angle)`), then the basis is re-orthonormalised. Rotations are in the camera's own frame, so there is no gimbal lock and no fixed horizon.
- **Roll.** Q and E keys, a slow automatic roll while drifting, and the two-finger twist gesture.
- **Speed.** `sp = min(world.speed, max(0.012, 2.6*dist)) * baseSpeed * (1 + 0.25*bass) * (1 + 3*boost)`, where `dist = |de(pos)|`. Velocity eases toward the target with rate 3.5 per second. Because speed is proportional to distance, the camera approaches surfaces asymptotically.
- **Wrap.** After moving, each coordinate is wrapped into one period of the current world.
- **Journey autopilot.** Runs when Journey is on and its movement setting `jMove` is `"travel"`. Probes `de` at four directions tilted from forward (right, left, up, down) at a distance proportional to `dist`, and steers toward the more open side: `lookX += (dR - dL)/(dR + dL) * 1.1 * dt`, plus a slow sum-of-sines wander. Forward thrust is 0.5 (drift is 0.3). With `jMove` set to `"drift"` none of this runs: Journey's clocks still change the scenery, and movement is whatever the user and the Drift toggle give. `jMove` is stored in `localStorage["mirrorfold-move"]`.
- **Handing control to the user.** All user look input (mouse, touch drag, arrow keys) goes through `userLook(dx, dy)`, which also adds the size of the turn to `userTurn`; the VR viewer's head turns add to it in `onGyro`. Each frame `userTurn / dt` is a turn rate in radians a second, and `userActive(act, rate, dt)` turns it into `lookAct` in 0..1: zero below 0.08 rad/s so tremor is ignored, full at 0.5 rad/s, rising in under a tenth of a second and fading with a time constant of about 0.7 s. The autopilot's steering and the idle roll are multiplied by `1 - lookAct`, and the automatic forward thrust (travel and drift) by `1 - 0.85*lookAct`. This applies in the VR viewer and in normal use alike.

## 8. Feedback, overlays, filters and transitions

This is the MilkDrop-style layer. MilkDrop's look comes from a loop: take the previous frame, warp it a little, fade it, draw something new on top, repeat. Then a composite shader recolours the result.

### Feedback (`FS_TRAIL`)

```
out = max(scene, warp(previous) * decay - 0.004)
```

The warp is applied to the UV used to sample the previous frame, in aspect-corrected space: rotation `uRot + uSwirl*(0.5 - r)`, zoom `uZoom`, a sinusoidal wobble `uWob`, a radial ripple `uRip`, then a drift `uDrift`. The `- 0.004` stops 8-bit values from sticking above zero. When a motion is active, `uShift` blends the trail toward its `brg` channel rotation each frame so trails change colour and read as distinct from the scene.

`MOTIONS` are parameter sets, expressed per frame at 60 fps and corrected for the real frame time (`pow(x, dt*60)` for decay and zoom, `* dt*60` for the rest):

| Motion | decay | zoom | Other |
|---|---|---|---|
| none | from FX | 0.994 | |
| Melt | 0.965 | 0.999 | wobble 0.0015, drift down 0.004 |
| Vortex | 0.96 | 0.992 | rotation 0.012, swirl 0.03 |
| Tunnel | 0.955 | 0.965 | |
| Implode | 0.95 | 1.03 | rotation 0.004 |
| Ripple | 0.955 | 0.996 | ripple 0.012 |
| Drift | 0.96 | 0.999 | wobble 0.001, drift sideways 0.004 |

**Drivers.** A motion from a pack or the editor may have `drive`, a list of up to two `{to, by, amount, every}`: one of `zoom`, `rot`, `swirl`, `wob`, `rip`, `dx`, `dy` follows a slow sine wave (`by: "wave"`, one cycle in `every` seconds, 8 at the least) or the pulse of the bass, mids or treble. `driven(mo, field, default, time, bass, mid, treble, scale)` in `js/packs.js` returns the number for this frame: the set value plus `amount * scale * half the field's range * signal`, then held inside `MOTION_LIM`, the same ranges `cleanMotion` uses. So a driven motion can never be outside what a plain one may be, and the quickest wave crosses a whole range in about 2.5 seconds at its fastest. `scale` is 0.25 under reduced motion. `decay` and `kick` cannot be driven, because trails that came and went with the sound would flicker. Filters have no drivers: a filter number following the beat (Negative, Solarise) would flash. The wave reads `clock.time`, so it stops under Hold still. The motion editor has two driver groups below its sliders (`edDriveBuild`, `edDriveRead`); what they say goes through `cleanMotion` with the rest. The built-in motions have none.

The **FX** button sets the base: glow (decay 0.78, bloom 0.55, fringe 0.004), trails (0.93, 0.75, 0.008) or clean (all zero). The decay used is the larger of the FX and motion values.

### Overlays

Drawn into the feedback buffer after the composite, so the motion smears them. Selected by `uOv` (1..7): Ring, Scope, Spectrum, Spokes, Rings, Spiral, Orbit (8 to 10 are the dancers, below). Sound data arrives as a 128x1 luminance texture `uWv`, refilled each frame by `updateWave()` with either the time-domain waveform or the frequency spectrum (overlays marked `spec` in `OVERLAYS`). With no live audio a synthetic shape is used. Colour is `pal(uHue + 0.3 + 0.45*r)` from the current palette. Strength is `uOvAmt` (15, 30, 50, 75 or 100%) and blends as `o += (max(o, colour) - o) * line * amount`.

**The dancers** (`js/dance.js`, `js/moves.js`; `uOv` 8 to 10: Dancer, Chorus line, Dance floor, marked `dance: 1`, `2`, `3` in `OVERLAYS`). Stick figures that dance to the music: one, with a deep floor to itself; four doing the same dance together; a crowd of eight to twelve (chosen each time the overlay is), each with its own. They are meant to move as a person in a suit with lines down the limbs would. Nothing about them is in the sound texture: JavaScript works out every joint and the shader only draws lines.

- *Keeping time.* `makeBeatClock` is given the bass's pulse each frame. A hit is the pulse rising 0.15 above where it had sunk to (and above 0.2, and at least 0.24 s after the last). The time between two hits is doubled or halved into `DN_FAST` to `DN_SLOW` (0.36 to 0.72 s, 166 to 83 beats a minute) and taken as the beat's length when within 18% of what is held (eased in by 0.3), or after three in a row that are not. The count `u` runs on at one a beat; a hit within 0.3 of a whole count pulls the count three quarters of the way to it, spread over the next frames, and three hits in a row that fall between the counts move the count to them. The count never goes backward. It is kept whatever overlay is chosen, so figures chosen later are in time at once. A tapped tempo is followed the same way, since it gives the same pulse.
- *A pose* is `MV_N` (28) numbers, listed at the top of `js/moves.js`: where the hips are (across, toward the viewer, lowered, off the floor), the whole figure's turn on the spot, the hips' turn over the feet and their tip, the chest's turn on the hips, the back's lean sideways and forward, the head's tip and nod; then each hand as a place (out from the neck, up along the back, forward of the chest) with how high its elbow is carried, and each foot as a place (out from where it stands, up, forward) with how far its knee is turned out. Hands and feet are given as places, not angles, because that is how a move is described ("hand behind the head", "foot out to the side") and because places can be mixed and eased in straight lines. Sides are measured outward, so `flipPose` turns a pose to face the other way by exchanging them.
- *A move* (`MOVES`, 143 of them, from the sway and the step touch through the twist, the sprinkler, the macarena, Y M C A, the moonwalk and the running man seen from the side, to the floss, the dab, the can-can and star jumps) is a list of keys: poses at given beats, each naming only what differs from standing (`MV_REST`). `movePose` finds the two keys either side of the beat. A move that gives a `hold` (the part of the time between keys it waits before going over), or has `hit` (eased twice, for moves that snap), or ends on a key of its own, goes from key to key eased and stops at each. Every other move flows: each number follows a curve through the keys with no corners (a Hermite curve whose speed at a key is the slope from the key before to the key after, going round the end of the move), so the figure does not stop on every beat. `sym` makes the second half of a move the first half facing the other way. `len` is 1, 2, 4, 8 or 16 beats. A key at beat `len` ends the last crossing (the spin ends a whole turn on); otherwise the move returns to its first key. `post` is a rule laid over the keys for things that go round (the hula, hand rolls, the lasso). `bob` is how far the knees give on every beat (`moveBob`; the give itself is added in `danceStep`, from the sound). `go` carries the figure along the floor to its own left, in figure heights a beat, and `sway` turns that back every so many beats (`moveGo`): the moonwalk glides backward, the duck walk goes forward, hammer time, the shuffle, Riverdance and a few others go to and fro. `lo`, `mid`, `hi` say how full the music must be for `pickMove` to choose it. A move is begun from its own first beat (`u0`), so the macarena starts at its beginning.
- *The body.* `danceBody` makes seventeen places in space from a pose: neck, hips, shoulders, elbows, hands, hip joints, knees, ankles, toes, head. The back is one bone from hips to neck, leaned and turned; shoulders and hip joints stand out from it. Arms and legs are each two bones to a given end (`bend`): the joint between is put off the line toward a chosen side, elbows back, out and down (higher with the pose's elbow number), knees the way the hips face (turned out with the knee number). So a crouch seen from in front shortens the legs, as it does on a person, and does not bow them. A hand asked for beyond reach is brought in; a hand asked for near its shoulder is moved forward and out, so that an arm raised from hanging to overhead goes up round the front (it is moved straight away from a point `DN_BACK`, 0.07, behind and inside the shoulder until it is `DN_CLEAR`, 0.17, from that point, so it is never nearer the shoulder than 0.1, and the one place with no answer is behind the shoulder blade); where a foot is too far for the leg the hips come down to it; a knee that would go through the floor bends upward. Every bone keeps its length. Last, the whole figure is turned on the spot. An elbow's side can change very quickly for a small move of the hand, so each figure keeps where its elbows were (`mem`) and an elbow swings only a share `10*dt` of the way each frame.
- *Seen from in front.* `danceFlat` drops the depth, making what is nearer the viewer larger by `DN_NEAR` (0.45 a figure height) about the height `DN_EYE`: enough for a foot stepped forward to sit lower and a hand held out to grow. A kick straight at the viewer still shows little, so the kicks in `MOVES` go out to the side as well.
- *What the figures hear.* A band's pulse is measured by `bandStep` against that band's own greatest level, which sinks only over tens of seconds, so after one loud moment, or with a quieter track put on in place of a louder one, the same kick drum is a pulse several times smaller. The other effects only grow weaker for that; the figures, which need a hit to be a hit, stopped. So `danceStep` measures each pulse against the strongest of the last few seconds (`st.pk`, `st.pm`, sinking with a time of 2.5 s, never under `DN_FAINT`, 0.06), and the count of beats and `pa` hear that. The knees and arms still give by how hard the kick is, but to a faint one at least half as much as to the hardest. With no kick to speak of they give to whatever part of the sound is keeping the beat (0.7 of the lead's onset). The count is kept by the seconds that really passed (`fr.raw`, up to 1), not by the frame's time cut to a twentieth of a second, so with slow frames it does not fall behind the music. With Stats on, a line says how much the figures are dancing, how sure the beat is and at what speed, whether there is sound, and how strong the bass pulse is (`danceSays`): if they stand when there is a beat, it shows which of these thinks there is none.
- *A steady beat or none.* The first clock here listened to the bass's pulse and judged its hits one at a time. A user's recordings of a live techno set showed why that fails: the bass rolled on with no clear kick, the beat was in the hi-hats, and the figures stood through all of it. Now `listen.js` gives four `onsets` (`onsetStep`): for four parts of the spectrum (`ONSET_BINS`: bins 1 to 5, 6 to 59, 60 to 159 and 160 to 400 of the analyser's 512), how much the bins rose since the last frame, kept as a number that jumps and dies away at `exp(-8t)`. `makeBeatBank` in `js/dance.js` runs one clock (`makeBeatClock`) on each, each onset measured against its own strongest of the last few seconds (never under `DN_FAINT2`, 0.004), so loudness does not matter. A clock keeps eight seconds of how much its pulse rose, in slots of a hundredth of a second, and five times a second (`look`) smooths that record over three slots either side and finds the beat's length between `DN_FAST` and `DN_SLOW` at which it best lies over itself: the score is the best of the mean likeness moved on by 1, 2, 3 and 4 beats, 0.9 of that by 2, 4, 6 and 8 (a hit every other beat) and 0.85 of that by 4 and 8 (a line that comes round only with the bar), with the top refined between slots. That score, less for a record under four seconds, is `conf`; `sure` goes toward `(conf - DN_SURE0)/(DN_SURE1 - DN_SURE0)` (0.22 and 0.4), quickly up and slowly down. The beat's length follows the best length when it is within 6% of what is held, or after four looks running that say another. Where in the beat the rises of the last four seconds pile up says where the count should be whole, and the count is pulled 0.35 of the way there each look, never backward. After a second and a half with no rise a clock begins its record again, so that what is played next is not mixed with what came before. The bank's own count follows the clock that is surest (`lead`), changing lead when another has scored 0.08 better for 0.8 s, or at once if the lead has lost the beat and another has it, and going over to the new lead's count a little each frame. In `tools/unit.mjs`: four on the floor, a kick on one and three, hip-hop, funk, dotted and breakbeat lines are each sure for over seven tenths of the time; uneven talk-like hits get the figures dancing for under an eighth of it; and a beat only in the top of the sound under a wavering bass is danced to. On the two recordings (run through a copy of the analyser, not kept in the repository) the figures dance from four or five seconds in, at 137 and 145 beats a minute, at 60 and at 30 frames a second. Not measured: music with no percussion at all.
- *From one overlay of figures to another.* Figures newly set up begin dancing as much as the last ones were (`st.amp`), so a change of overlay while the music plays does not send them back to waiting. The count of beats and how sure it is are kept across the change.
- *Standing or dancing.* `pa` is the last second's average of the bass's pulse (or 0.6 of the mids'); `go` is 0 with `pa` under 0.03 and 1 over 0.12, times `ease((sure - 0.7)/0.25)`: there must be sound, and a steady beat in it; `en` follows `go * (0.45 + 0.55*level)` over 0.8 s, where `level` is `heard.level` from `js/song.js` (how full the music is in its own range), or 0.6 with no sound to read (a tapped tempo). The pose shown is the pose of a figure that is not dancing (`idle`, below) moved `d.a` of the way to the move's; each figure's `d.a` follows `ease(e/0.4)`, `e` being `en * (1 + 0.4*hype)`, at `2.5*dt`: so the figures are either standing or dancing with a short way between, since half a move is not a move. How full the music is shows in which moves are chosen (`e` under 0.55 the quiet ones, under 0.85 the middle ones, over it the liveliest).
- *The floor.* Places on it are in figure heights: across from the middle, and away from the viewer from the front edge, where a figure is drawn its full size (`front` gives that size for the overlay and the picture's shape). `place` puts a place in the picture: a figure `z` deep is `1/(1 + DN_DEEP*z)` as large (`DN_DEEP` 0.3), stands higher by `DN_UP` (1.5) figure heights times what it has shrunk by, as a floor looked down on does, and is dimmer (to 0.45 at the limit). Nothing is ever nearer than the front edge, so nothing is larger than there. Each figure has a place of its own (`homes`, `homeX`) and is `tx` across and `tz` deep from it. The dancer alone starts at the middle of the front edge and may be anywhere on a floor `DN_FLOOR` (4) deep and as wide as the picture shows at each depth (`span`); the chorus line stands in a row at the front and may go 0.5 either side; the crowd stands in three rows 1.2 apart, a quarter in front, a third in the middle and the rest behind, each moved a little from its rank by chance, and each may go 0.4 across and 0.3 deep from its place (`bounds`).
- *With no beat* (`idle`). Each figure waits for three to nine seconds, or (not the chorus line, which keeps its places) walks to another place on the floor chosen by chance (`spot`: anywhere for the dancer alone, within 0.7 across and 0.5 deep of its place for one of the crowd) and waits there. Waiting (`waitPose`), it faces a way of its own choosing, its weight goes slowly from foot to foot, its head looks about, and every two and a half seconds a foot is lifted and put down. Walking (`walkPose`), it faces the way it goes, toward the viewer, away or across, at `DN_WALK` (0.3 heights a second); a foot on the floor goes back under the body exactly as fast as the body goes forward (a step is `DN_STEP`, 0.2), so it does not slide. A figure turns at `DN_TURN` (3 radians a second) at most and walks only as far as it faces the way it is going. When the beat comes, a figure outside the room it dances in walks back first, at 1.8 times the pace, and only then begins.
- *Moving about and turning while dancing.* With each move a figure chooses (`carry`) a place to go to (`spot`) and moves toward it at `DN_DRIFT` (0.3 heights a second) at most, easing in and out; a move that travels (`go`) carries it across instead, more slowly as it nears the end of its room. It also chooses how to face: it starts the move up to 0.4 radians from where the last left it, and in two moves of three turns slowly on the spot, one way or the other, at 0.08 to 0.3 radians a beat (`d.sp`), so over a minute it is seen from every side; with its back to the viewer it always keeps turning. A move that travels comes round, at 1.2 radians a beat, to face as the move itself says, since the way it goes depends on that. A figure that begins to dance begins facing as it stood, and one that stops stands facing as it danced; the turn between the two is kept going the way it was going (`d.dw`), because the short way round can change sides from one frame to the next. The chorus line turns and moves as its first figure does. The jump at a drop is made facing whichever way the figure was.
- *On the kick.* The count says where in a move the figure is; the bass itself says when the body gives. `st.kick` follows the bass's pulse, up within a frame or two and down over a seventh of a second, and each frame the knees give by the move's `bob` times `0.3*(the count's own cosine) + 2.4*kick`, the back tips forward by `1.5*bob*kick` and the head nods by `6*bob*kick`. So a kick drum that lands early, late or twice is seen landing, whatever the count thinks.
- *What the body does whatever the move* (`groove`). Laid over every move's pose, sized by numbers each figure chooses anew for each move (`carry`: how widely it sways, where in the beat, which footwork, how hard the arms hit, where on the floor it drifts to), so no two times through a move are alike. The hips sway over two beats, tip and turn with it, and the shoulders turn against them, with a quicker turn once a beat; the weight goes from foot to foot, and the foot it has left lifts at the heel with its knee coming in, or takes a small step to the side, or shuffles forward and back (the three footworks), by as much as the move itself leaves the feet alone; the head tips with the sway and nods on the kick; each hand is pushed out along its own line from the shoulder on the kick (`st.kick`) and flicks on the mids (`st.snap`), with the elbow lifting; and slow small wanderings in the hands and the back, on periods of three, five and six beats, keep a loop from repeating exactly. A figure dancing on the spot also drifts toward a place of its own near where it stands. The chorus line all carry a move as their first figure does.
- *Kinds of dancing.* `MV_STYLES` in `js/moves.js` puts every move in exactly one of seven kinds: `groove` (what people do on a dance floor without thinking), `disco`, `sixties` (the twist, the swim, the hand jive and so on), `hiphop`, `party` (the mimes and the dances everyone does together), `world` (Latin, folk and jazz steps) and `rave`. `setDanceStyle` keeps the figures to one (`danceStyle`; `"any"` is all), and each then takes a routine of that kind at its next move; `makeRoutine` takes every move of a kind that has fewer than three fit for the music. It is a Journey category (`dance`, "Dance style", every 60 seconds), so a template can keep to some kinds or go round them; there is no control for it outside Journey.
- *Routines.* A figure does not pick one move after another at random. `makeRoutine` gives it three to ten different moves fit for how full the music is, each with whether it is faced the other way, and `nextMove` takes it through them in order, each for its own length (four beats at least), twice; then a new routine is made. A new one is made at once after a great change in the sound (`soundChanged`) and after a drop's jump, and at the end of a time through if the music's fullness has moved to another of the three kinds. The chorus line dances its first figure's routine in the same frames, and every other time through, every other one faces the other way. One move is crossed to the next over a beat, and never while the last crossing is still going.
- *Travelling.* Each figure has `tx`, how far it is from its place in figure heights. A move with `go` moves it, more slowly the nearer the end of its room (`room`: 0.9 for the dancer alone, 0.5 for the chorus line, 0.3 on the dance floor), so it never gets there; such a move is faced so as to bring the figure back toward its place, and the chorus line all go the same way. A figure dancing on the spot drifts over a couple of seconds toward the place it chose for that move (`wx`), and one standing still comes back.
- *Drops.* On `heard.drop` every figure jumps (`jumpPose`, `DN_JUMP` 2.2 beats: down, up with the arms thrown high, down), `hype` is set to 1 and falls over ten seconds, and each takes a new routine afterwards.
- *Never a jump.* Whatever the rules above ask for, each figure's 28 numbers go only a share `13*dt` of the way to it each frame (the turn the short way round), a hand or foot no faster than `DN_QUICK` (4 heights a second) within the body. Last, an elbow or hand is shown going no faster from its shoulder than `DN_TOP` (5): where a hand passes close by its shoulder the elbow must swing a long way in a frame or two to keep both bones their length, which showed as a flick, so for those few frames the arm is drawn a little short or long instead. (`danceBody` itself always keeps the lengths.) `tools/unit.mjs` checks that every bone keeps its length in every move and in random poses, that every move comes round in its own length, that no move alone asks a joint for more than seven figure heights a second at 150 beats a minute, and, through silence, a minute of music, a great change, a drop and quiet again, that no joint moves faster than that, that the figures stand in silence and leave the floor at a drop.
- *Drawing.* `danceSpots` gives the figures' own places in the picture, in units of its shorter side; `DN_SIZE` (0.65) scales them all. `danceFill` writes nine `vec4[12]` uniforms (`uD0` to `uD8`, 108 vectors: `DN_MAX` is 12, and the shader's arrays and loop are written to that number), the figures furthest first: neck and hips, the shoulders, each arm's elbow and hand, the hip joints, each leg's knee and ankle, the toes, and the head's middle, radius, and one number that is the figure's own number plus half its brightness (0 for none). In `FS_TRAIL` each figure is the nearest of fourteen lines (`limb`), a filled head and a small filled hand at the end of each arm, looked at only within eleven head radii of its hips across and thirteen up or down, so a pixel works out only the figures near it. Each is drawn over the ones before it: its line and its dark edge hide theirs, so a nearer figure covers a further one. Unlike the other overlays the figures have a dark edge (`dk`: what is under them is dimmed out to 1.6 line widths), because a thin figure made only of added light is lost against a bright world. Each figure's colour is its own place in the palette (the shader sets `rr`, which the colour is read from, from the figure's own number, so a figure keeps its colour as the order changes). With a video in the overlay the lines are three times wider, not seven.
- *What stops them.* Hold still: `stepDance` returns, so they stay as they are. A loop being flown: `danceFill` hands the shader no figures, because the moves are chosen by chance and would not come round. With less motion asked for they dance at half speed and smaller. In the VR viewer they are flat, at the overlay's own depth, like a pack overlay. Flying together, each person's figures are their own: only the overlay's name is the host's.
- *Not tested.* How well the count follows real music beyond one user's report that the figures react well. The moves were looked at as rows of still poses and never in motion, so how each reads when danced, and whether its timing sits on the beat as the real dance does, is not known. Nor is the frame rate on a phone with five figures (up to 75 distances a pixel inside a figure's column).

### Bloom

`FS_DOWN` averages four taps and keeps what is above 0.5. Each tap sits on a corner between four full-size pixels, so the four together average all sixteen pixels under a quarter-size one: a small bright point cannot be missed in one frame and caught in the next. (Weighting the taps by brightness, as bloom over a wide brightness range needs, was looked at and left out: the pictures here are 8 bits, so nothing is brighter than 1.) `FS_BLUR` is a 9-tap Gaussian run horizontally then vertically at quarter resolution. Strength is `fx.bloom * (1 + 0.7*bass) + 0.5*warp`.

### Filters (`FS_FINAL`)

Applied in this order. `LOOKS` entries set one or more of these uniforms.

1. Transition coordinate warp (below).
2. Coordinate filters by `uFx`: Quad (`abs`), Tiles (mirrored 3x3), Bulge, Twirl.
3. Liquid (`uLiq`, sinusoidal displacement) and Mosaic (`uMos`, cell quantisation).
4. Sampling: four taps along the zoom-blur direction, with red and blue sampled at slightly different scales for colour fringing (`uCA`).
5. Echo (a flipped, 2x ghost), Neon (four-tap edge detect), Solar, Negative, Prism (hue rotation growing with radius and time), Poster.
6. Colour filters by `uFx`: Thermal (luminance through the palette), CRT, Halftone, Contour, Noir, and six made with video in mind: Comic (four levels a channel with dark outlines), Two-tone (two palette colours by brightness), Tape (rows shifted, colours out of register, a slow rolling band, faint grain), Streaks (bright parts run downward), Emboss, and Glass (15, a grid of small lenses, applied with the geometric ones).
7. Bloom is added, then the transition tint and mask.

### Transitions

A world change (and a journey mirror change) runs `warp` from 0 to 1 over 0.5 s, performs the change at the peak, and returns to 0 over 0.8 s. `beginWarp()` picks one of eight types at random, never repeating the last: swirl, dive, blocks, fold, melt, blink, tear, dissolve. All but blink and dissolve finish in a wash of the current palette colour at the peak, which hides the swap and the shader-compile hitch. `requestWorld(i)` starts a transition to a world; `warpThen(fn)` runs any function at the peak.

## 8b. Hold still

`js/still.js`. The **Hold still** switch (`still`, `setStill`, key H) is a pause and a way to get a clean frame.

**The pause.** In `frame()`, `tickClock`, the autopilot and `stepJourney` are skipped while `still` is true, so the time, the morph, the colour drift and the mirror spin stop, and Journey changes nothing. `turn` and `move` drop the automatic roll and the drift, bring the look, the roll and the velocity to an exact stop (they otherwise ease toward zero for ever), and still obey the stick, the keys and the pointer. The sound is still read, so the glow and the motions keep following the music. Turning Journey on calls `setStill(false)`.

**The sharpening.** `stillAim(fr)` runs before `drawScene`. If the camera's position and directions and the morph are within 1e-9 of last frame's, and the world, picture size, mirrors, palette and VR setting are the same, it counts one more frame (`stillN`, up to `STILL_MAX` = 32); otherwise it starts again at 1. It also sets `jit`, a shift of up to half a pixel each way from the Halton sequence (bases 2 and 3, 64 places). The scene shader adds `uJit` to `gl_FragCoord` where it makes the ray (and where a cloud world picks its first step), so each frame looks through a different part of every pixel. While `stillN` is not zero `drawScene` passes no sound to the scene and the field of view does not pulse, so the frames match.

`stillBlend()` runs after `drawScene`: `FS_ACC` moves the kept picture `tR` a share `1/stillN` of the way to the new frame in `tA`, then the kept picture is copied back into `tA`, so every later pass (the land laid over, trails, glow, filter) works on it unchanged. The pictures are 8 bits a colour, where a share of 1/32 of a small difference rounds to nothing; `FS_ACC` adds half a level of noise that differs every frame, so the rounding is right on average. Once `stillN` reaches 32 the share stays at 1/32, so a slow change (the palette easing to a new choice) is followed with a lag of about half a second.

Not sharpened: the land alone, and anything with a video (the frames differ). The land laid over a world is not sharpened but the world behind it is. In the VR viewer it works as on a flat screen, because nothing in it is centred on the screen. Measured only in headless Chrome; whether a phone holds 60 frames a second while it runs (two extra full-size copies a frame) is untested.

**Lens blur** (`lensI`, `LENS`: off, soft, strong). With it on, each of the averaged frames is also seen from a different place on a lens. `stillAim` picks the place (a disc filled evenly by the Halton sequence in bases 5 and 7) and hands the shader `uLens`: the place, across and up in world units, and the sharp depth. In the scene shader a ray then starts at that place and is aimed through the point its pixel would have seen at the sharp depth, `ro += uCam*(lens,0)`, `rd = normalize(uCam*((uv,fov)*depth/fov - (lens,0)))`, so everything at that depth lands on the same pixel in every frame and everything else is spread over a disc. The sharp depth is found once when the scene comes to rest (`lensFocus`: the world's JavaScript `de` walked straight ahead; a cloud world uses 0.5 and a pack world four times the distance to the nearest surface, having no `de` to walk). The lens's radius is `a` times the sharp depth, or times three times the distance to the nearest surface if that is less: tied to the sharp depth alone, a view down a long tunnel smeared the near walls away. The kept picture takes up to `STILL_LENS` = 128 frames with the lens, since 32 places on it show as copies. The world beyond a doorway gets the same lens scaled by the doorway's `s`. Off in the VR viewer, over the land and in the zoom worlds. Looked at in Temple, Julia and Sponge.

## 8c. Record video

`js/record.js`. `recStart()` takes `canvas.captureStream(30)` and, if the audio context is running, adds the audio track of a `MediaStreamDestination` joined to `master`, so the recording has whatever the app itself is playing. While the app listens to a tab or the microphone `master.gain` is 0, so that sound is not recorded, which is as it should be: it is not the user's to republish through this page. A `MediaRecorder` gathers a part a second into memory; `recStop()` (or the limit `REC_MAX`, 300 seconds) joins them into a file and saves it through a download link. The file kind is the first of `REC_TYPES` the browser accepts (MP4 where it can, otherwise WebM). The button is hidden where `captureStream` or `MediaRecorder` is missing.

It records what is drawn, at the size and rate it is drawn, so a phone that is struggling makes a struggling video. Checked in headless Chromium in real time (the recorder gives nothing under virtual time): four seconds gave a 1.7 MB WebM. Untested: any phone, Safari's MP4, whether the sound is in step with the picture.

## 8e. Photo mode and postcards

`js/photo.js`. **Photo mode** (`setPhoto`) turns Hold still on and shows three sliders, each -100 to 100 and turned into a multiplier by `photoGain`: Zoom multiplies `fovNow` in `drawScene` (up to 2.6 either way), Brightness is `uExp` in the scene shader, multiplying the light before the tone curve (up to 2.8), and Focus multiplies the sharp depth `lensFocus` found (up to 4). All three are 1 outside photo mode. `photoKey()` is part of what `stillAim` compares, so moving a slider starts the kept picture again. `photoFrame`, the last step of `frame()`, leaves photo mode when Hold still is let go.

**Save large picture.** `setShot(px)` in `js/targets.js` makes `resize()` size the canvas and every picture so that the long side is `px` (3840, or 2560 on a touch device), held to `MAX_TEXTURE_SIZE` and `MAX_VIEWPORT_DIMS`; Detail auto is told to leave it alone. The frame loop then simply runs at that size under Hold still. When the kept picture is full (`stillMost()`), or after `PHOTO_WAIT` (25) seconds, `photoFrame` asks `pictureMake` for the frame, saves it, and `setShot(0)` puts the size back. Every picture the app holds is that size meanwhile, about 33 MB each at 3840 by 2160; whether a phone survives it is not known, and a lost context is handled as it always is (the page asks for a reload).

**Postcards.** `pictureCard(fn)` in `js/picture.js` hands the canvas to `fn` in `pictureFrame`, while the frame is still on it. `cardDraw` copies it into a 2D canvas with a strip underneath: the world's name, the palette's, the spot's code (`encodeSpot()`, set out in fours by `cardSpaced`) and the QR code of the link to it. The strip is made tall enough for the code's squares to be three pixels each. The PNG gets the scene put in it as Save picture's does. **Go to a code** reads typed text through `cardCode` (spaces out, capitals down, then it must be a world's name, a hyphen and 16 to 18 letters and digits, and the world must be one the page has) and sets it as the address's hash, so it goes the way any link's spot does.

**The QR code** (`js/qr.js`, free of the page). Byte mode, level M, sizes 1 to 9 (up to 180 letters), with the block and check-byte counts and alignment places of the standard in two small tables, Reed-Solomon check bytes worked out by `qrCheck`, and one fixed mask (the chequerboard), which the format bits name. Tested: `tools/unit.mjs` has the standard's own worked example for the check bytes and the fixed parts of the square; codes of seven lengths, one for every size from 1 to 9 but 2, 3 and 5, were read back correctly by OpenCV's reader, as was the code on a postcard made in headless Chrome. Not tried with a phone's camera.

## 8f. What was playing, and passing things on

`js/media.js`. `mediaNow()` gives what is playing as `{kind, title, at, seed, bpm, video}`, or null if **Music named in what I share** is off. The page knows it only for what it plays itself: the built-in music (`builtNow()` in `js/music.js`: the number the song was made from, kept as `songFrom`, and the step it is at; a song made by chance is now given a number first, so that it too can be had again), an audio file (`mediaFile` is told the name when one is chosen; `pPos()` is the time) and a video file (`mediaVideo`, `vidTime()`). Sound from a tab, another app or the microphone reaches the page with no name, so **What's playing?** keeps a typed line (`setNote`) and the time it was typed; the moment in the song is counted from then. A typed line stands in place of a file's name but not of the built-in music.

It goes into a scene as `media` (`sceneNow`), so every picture, large picture and postcard has it; a postcard prints `mediaText` of it; and a recorded video, which a browser cannot write tags into, gets `mediaSlug` of it in its file name, taken when the recording began. Coming back, `cleanScene` passes it through `cleanMedia` (in `js/packs.js`, with the other cleaners): a kind from `MEDIA_KINDS`, a title that is one line of at most 80 characters, numbers in range, and if any part is wrong the whole of it is left out and the scene kept. `goScene` then calls `mediaGo`: the built-in music is started as that song at that step (`builtGo`); an audio file is moved to the time if it is the one in use, and otherwise the time waits (`due`) for a file of that name to be chosen; anything else is only said. The title is shown through `toast` (`textContent`) and `fillText`, never as markup.

`js/send.js`. `sendOffer(o)` shows a row for a postcard or a video that has just been made. **Share** calls `navigator.share` with the file, and is hidden unless `navigator.canShare({files})` says yes. The file is made first and shared on a second press, because a browser opens the share sheet only in direct answer to a press and making a postcard takes a frame and two asynchronous steps. **Post to Reddit** saves the file and opens `https://www.reddit.com/submit` with `title` and `url` in the address (`sendReddit`): a page cannot give a file to another site, so the picture is added there by hand. Nothing is sent by the page itself.

Tested: the cleaner, the text, the file-name part and Reddit's address in `tools/unit.mjs`; in headless Chrome, the built-in music noted and started again at the same step, a typed line with its time, the switch turning everything off, a scene with a hostile title loading with the title as text, the row appearing, and a postcard with the line on it looked at. Not tested: the share sheet (headless Chrome has none), Reddit's page, a real audio file.

## 8d. Record a loop

`js/lap.js`. A flight that ends where it began, saved as a video that repeats with no join. It rests on the rule that every world is exactly periodic.

**The path** (`lapPlan`, when the button is pressed). Three kinds. *Line*: one whole period along an axis, which ends at a copy of its start. `lapLine` tries the way through the camera's own place first and then 24 by chance along each axis, walking each with `de` (`lapClear`: steps of 0.7 of the distance, never less than 1/160 of the way), and takes the one with the most room, preferring the camera's own and the axis it faces. The place is kept as parts of the period, so a world whose period changes with the morph still closes. *Ring*: where no line is clear (Box and Cell, of the built-ins), once round a circle in the most open of 160 places (`doorSpot`), of radius 0.45 of the room there. *Deep*: in the descent, from `3*DP_IN` grids out to `DP_IN` along the nearest axis, in equal times for equal shrinking; the picture is then the same three times smaller, and `lapFrame` reports the move outward in `fr.jump` as `move` does. On a line and in the descent the camera rolls over once and looks a little from side to side (`lapPose`); neither where less motion is asked for. A pack world has no `de` to walk, so its lines are judged from 24 places along each, asked of the chip together (`deMany`). A lap takes the path's length over half the speed the room allows, held to 8 to 24 seconds.

**Everything else must come round too.** While `lapOn()`, `frame()` skips `tickClock` and `lapClock` sets the clocks from the lap's phase `u`: `clock.time`, `clock.hueT` and `clock.morphT` each swing out and back as `sin(2*pi*u)` (the morph's clock by `LAP_SWING` = 4 seconds either way, after the path has been checked clear at both ends of the swing, with `pkTick` set for each so that the packing's wave is checked too; if it is not clear the morph is held); `clock.spin` goes through a whole number of mirror folds, after each of which the mirrored picture is the same; the sound in `fr` is replaced by `lapBeat`, a soft pulse about every 1.2 seconds, so the video has the life the music gives without the music. Journey's steps are skipped. `worldPass` leaves out the orb, the thrown light, the sprites, friends and ribbons, `stepOrb` does not collect, and doorways are closed and refused, because none of those would be back in place. `lapFrame` runs after `move` and `flightFrame` and puts the camera on the path, as a played flight does; any steering ends the loop, as does Hold still, a change of world or packing, the land, or the VR viewer.

**Recording.** The lap's phase starts `LAP_LEAD` = 4 seconds before 0, behind a transition, so that the feedback trails have settled into what they will be a lap later. At phase 0 `recBegin` starts a `MediaRecorder` on `canvas.captureStream(0)` and `lapShot`, the last step of `frame()`, hands it each finished frame with `requestFrame()`; where the browser has no `requestFrame` it takes frames at its own pace (30 a second). At phase 1 the recorder is stopped and the file saved, and the loop flies on.

**Tested.** `tools/unit.mjs`: `lapClear`, `lapLine` and `lapPose` against a made-up world, that each kind of path ends as it began, and the pulse. In headless Chrome, with frames of equal length: the finished picture at five moments of one lap against the same moments of the next was identical to the last pixel in Sponge (with the Vortex motion and three mirrors), Temple (whose period follows the morph), Klein with grain, nested Julia with Pulse wave, the descent, Cell (a ring) and Nebula (a cloud world); the recorder started, was handed every frame of the lap, and saved. A node script over every built-in world at three morphs found a line in all but Box and Cell, in every packing, in under 15 ms. Not tested: a real device, where frames are not of equal length (the trails then differ slightly at the join), the saved file in any player, and `captureStream` without `requestFrame`.

## 8g. The eye

`js/eye.js`. A human eye that fills the screen, with the world showing only in its pupil. It was asked for as "a world, a land or an overlay", and is none of them: an overlay is drawn into the trails and is bent by the motion and the filter, and a land is part of the scene, so either would have had the overlays and filters running over the eye. The eye is a fifth pass, after the final one. While it is on, `drawFinal` draws the finished picture into `tE` (or into `tF`, when the flash limiter is on) and `drawEye` then draws the eye to the screen, reading that picture in the pupil. So the world, the land, the motion, the overlay, the filter and the transitions all live in the pupil, and nothing is drawn over the iris, the white or the lids.

**Settings** (five buttons in the Look group, kept in this browser as `mirrorfold-eye`, `-eyezoom`, `-iris`, `-blink`): `eyeMode` (`EYES`: off, on), `eyeZoom` (**Eye nearer** and **Eye further**: a step from 0, the whole eye, to `EYE_STEPS`, 6, where the iris fills the picture; it starts at 3), `irisI` (`IRIS`: follows the palette, or one of five colours of its own, each three colours: round the pupil, the body, the rim), `blinkMode` (`BLINKS`: off, now and then, changes the world).

**How near** (`eyeRadius(step, asp)`): the iris's radius, where the picture's shorter side is 1, goes from `EYE_FAR` (0.2) at step 0 to `eyeFill(asp)` at the last, each step multiplying it by the same amount. `eyeFill` is 1.04 times the way from the middle of the picture to its corner, so at the last step the iris covers the whole picture, wide or tall, and the lids are out of it. `drawEye` eases `ey.z` toward `eyeZoom` (there and not in `stepEye`, so the buttons work under Hold still). Seen from very near, a pupil of its usual size would take the whole of a tall picture and leave the iris only the corners, so `eyePupil` holds the pupil as drawn to about a third of the picture's shorter side (`EYE_PUPIL`), still opening with the sound; the fibres run from that pupil's edge, so they fill what the pupil gives up.

**The shader** (`FS_EYE`) works in units where the picture's shorter side is 1, with the eye in the middle.

- *The lids* are two curves, `up` and `lo`, that meet at the corners (`W` either side). `uBlink` (0 to 1) takes the upper one down to `shut`, a line a little above the lower lid, which rises to meet it. `open` is the distance inside the nearer lid, below zero on the skin.
- *The pupil* (radius `uPu` of the iris's) shows the middle of the finished picture, somewhat smaller than life (`hf`: a small pupil shows about half the picture's shorter side, a large one nearly all of it), bulged a little toward the edge, read four times a pixel because it is made smaller, and darkened at its rim.
- *The iris* is noise in the angle round the pupil and in `t`, which runs from 0 at the pupil's edge to 1 at the rim, so the fibres stretch as the pupil opens. `vn(p, per)` is value noise whose second number comes round every `per`, so it wraps round the circle with no seam; every use of it here gives a whole number for `per`, and anything added to the angle is itself made that way. Two ridged noises (`f1` fine and stretched outward, `f2` coarser and crossing it) make the network; a slower noise `w` bends both, and `uMo` (the clock, and the world's morph) moves it, which is what changes the network's shape. The three colours are worked out in JavaScript (`drawEye`): three places along the palette in use, or the iris's own.
- *The white* is a little of the palette's colour (16%) over off-white, darker and pinker toward the corners, with the pink corner by the nose. *The blood vessels* are the lines where a noise crosses its middle value: the noise changes quickly round the eye and slowly outward, so the lines run outward and wander, and there are more of them, and thicker, toward the corners. `uVes` moves the noise that bends them: slowly with the clock, and with the eased level of the mids. They thicken a little on the beat.
- *The surround.* A first version drew skin, a fold above the lid and lashes; the user found the skin looked odd, so the view stays close in and what little shows beyond the lids is a bumpy surface of pores in the palette's colour. `surf(p, c)` is its height: low swells, and to four squares in five of a grid a pit with a raised rim, off-centre by chance and of its own size. Each pore opens and shuts as `sin` of its own phase plus `uPor` times its own speed, so no two keep step; `uPor` (`ey.por`) runs on in `stepEye`, slowly by itself and in a surge on each beat. A pore and its rim reach at most 0.62 of a square from a middle that is at most a quarter off-centre, so the nine squares round a place hold every pore that can reach it: a larger pore shows the squares' edges, and so does a radius of nothing (`smoothstep` with equal edges has no answer), which is why a square with no pore still has a radius. The surface is lit from the upper left from the slope of `surf`, taken at three places. Each lid's part is moved with that lid, so a blink carries the pores down with it.

**What moves it** (`stepEye`, a step of `frame()`): the blink (`blinkStep`: shut in `BLINK_SHUT`, held `BLINK_HELD`, open in `BLINK_OPEN`, then a wait from `BLINK_GAP`, all doubled when reduced motion is asked for; the lid follows a curve that starts and ends gently, and `tools/unit.mjs` holds it under a sixth of the way a frame); the gaze, which follows the turning of the view (`fr.lx`, `fr.ly`); the pupil, which opens with the low end; and the pores' clock `ey.por`. Everything else comes from `clock` and the frame's sound. Hold still stops `stepEye`, and its clocks are already stopped. While a loop is flown the lids stay open, the gaze is ahead, and the pupil and the pores take the loop's own beat and clock, so the lap comes round.

**A blink that changes the world** (`blinkShut`, with Blink set to "changes the world"): about every half minute, at the moment the lids come shut, `setWorldNow` is called with no transition: the lids are the transition. The world is Journey's choice (`jPick`) where Journey is choosing worlds, and otherwise any other world. It is not done while a transition is running, a doorway is owed, a flight is being played or a host is being followed.

**Not in the VR viewer**: it is flat on the screen, and each eye would see half of it (`eyeShown`). It is not in packs, scenes, Journey's templates, share links, recorded flights or Fly together: it is this browser's setting only.

## 8a. Video (an experiment)

`js/video.js` shows a video file the user picks, or the camera, in the picture. Nothing is uploaded or kept, and a pack cannot name a video. The frame step `videoFrame` runs before the drawing steps; `videoUniforms` hands the result to the scene shader and the trails pass on texture unit 5 (`uVid`, `uVidK` = way, strength, fit to screen; `uVidS` = repeat scale on surfaces).

Six ways (`VMODES`), chosen with the "Video …" button:

| Way | Where | What it does |
|---|---|---|
| on the surfaces | scene shader | Laid on from the three axes, weighted by the normal. Each copy is the mirror of its neighbour, and a pair of copies fits the world's period a whole number of times, so it survives the camera wrap. True 3D, so it stays on in the VR viewer. |
| through the shapes | scene shader | Flat on the screen, used as the surface colour and lit more evenly. The video stays recognisable with the world embossed into it. |
| in the distance | scene shader | Takes the place of the fog colour, so far things fade into the video. Only shows on open worlds. |
| in the overlay | trails pass | The overlay's shapes are drawn seven times wider (`wd`) and replace what is under them with the video. Works with pack overlays too. |
| as the colours | scene shader | The surface colour is read from the video at a point given by the orbit trap, so the fractal is striped with the video's colours. True 3D. |
| filling the screen | its own program (`videoScene`) | No world is drawn: the video is the scene, fitted to the screen, folded by the mirrors exactly as a world is, and swelling 2.5% on the beat. Motions, filters, overlays and transitions then work on it as on any scene, and the land can stand in front (Land over). The camera still flies the unseen world, so the land moves. Orbs are off. In the VR viewer the world is drawn instead. |

**The flash limit.** The shaders never read the video itself. They read `tV`, a 640-wide copy that `videoFrame` moves towards the newest frame. Each frame a 4 by 4 picture of the new frame's average colours (`pMean`, read back into `mNew`) is compared with the same averages of the copy (`mOut`, tracked in JavaScript, since the blend is linear). The blend amount is cut so that no sixteenth's average changes by more than 0.6 of full brightness a second (0.3 with reduced motion). Measured: a clip strobing black to white at 5 Hz comes through as a ripple of about 6%; ordinary footage is followed within a level or two; a hard cut becomes a fade of up to a second. Do not hand the raw texture to any shader.

**Sound.** Music has a source `video` ("My video's sound"). Choosing a video file selects it only if Music is off; the "Video sound" button (`bVidSnd`) switches between it and the source that was playing before (`musicBefore`), so a video can run silently under any other music. `videoSound(on)` joins the video element to the audio graph with `createMediaElementSource` the first time, and from then on mutes or unmutes the element; `liveAudio()` counts it, so the beat reading follows the video. Any other music source mutes the video. The camera has no sound. Checked in headless Chrome only (sound reaches the analyser; the video keeps playing while the audio context is suspended); iPhone untested.

Not done: the land (it ignores the video; only the overlay way works over it), cloud worlds (same), a journey category, remembering the choice, any test on a real phone. The smoke test does not cover it, because headless Chrome's virtual clock does not run a video; it was tried with Playwright and three made-up clips.

## 9. Palettes

Cosine palettes: `colour(x) = a + b*cos(2π*(c*x + d))`, four `vec3` parameters per palette. The shader's `pal()` reads them from uniforms `uPa..uPd`. The live values `palCur` ease toward the selected palette at rate 1.6 per second, so palette changes are smooth. The phase `uHue` drifts slowly and faster with treble.

The first eight palettes are always available. The other six are unlocked one at a time by collecting orbs; the count is stored under `localStorage["mirrorfold"]`. Palettes added from packs follow the built-ins and are always available (see Packs in section 11).

## 10. Audio

### Graph

```
built-in music (js/music.js):
  kick, clap, closed hats -----------------------------+
  pad -> filter -> gate -+                             |
  arp, lead, riser ------+-> tone filter -> duck ------+-> compressor -> air filter -> out -+
  echo and reverb -------+                 (pumps)     |                                    |
  bass -> subDuck (pumps deeper) ----------------------+                                    |
orb chime, file (buffer source or media element) ------------------------------------------+-> bus -> analyser -> master -> destination

shared tab or microphone -> cap.gain -> analyser      (master gain is 0 while listening)
```

One `AnalyserNode` (FFT 1024) sees whatever is playing. `ensureAudio()` builds the graph on first use.

### Sources (`setMusic(mode)`)

- **built**: a dance track made up as it plays (`js/music.js`), 126 BPM, natural minor. `tick()` runs every 90 ms and schedules sixteenth-note steps 350 ms ahead on the audio clock with `playStep`. A song is 72 bars from `PLAN` (intro 8, build 8, drop 16, breakdown 8, build 8, drop 16, outro 8); `newSong()` then picks a new key, one of five four-bar chord loops (`PROGS`), a gate rhythm, an off-beat or rolling bass, an arp shape and a one-bar tune. The sounds are all oscillators and filtered noise: a kick (sine dropping from 165 to 44 Hz with a noise click) on every beat, which also ducks the `duck` and `subDuck` gains and lets them recover over about a fifth of a second (the sidechain pump); a clap (three bursts and a tail) on beats 2 and 4 of a drop, gathering pace through a build; hats; a saw-and-sine bass; the chord as three detuned saws a note, chopped by `gate`; an arp whose rests come from a Euclidean rhythm; a lead; a noise riser into each drop and an impact on it. A build ends with half a bar of silence. `musicFollowsSpeed` opens the last low-pass filter as you fly faster. `musicRender(ctx, bars)` schedules a song into an `OfflineAudioContext`, which is how the mix was checked: the author cannot hear it, so levels were measured bar by bar (peak 0.82 before the master gain of 0.5; breakdown about half the loudness of a drop). How it actually sounds is untested.
- **file**: `decodeFile` reads the file and decodes it into an `AudioBuffer`, played by a looping `AudioBufferSourceNode`. Seeking is stop-and-restart at an offset, which is exact. Because a decoded hour of stereo audio is over a gigabyte, the file's length is probed first with a media element: anything over 15 minutes, or over 80 MB, or that decodes shorter than its reported length, plays through the media element instead (`useElement`). The `player` object abstracts the two (`pPlay`, `pPause`, `pSeek`, `pPos`, `pDur`).
- **tab**: `getDisplayMedia` with audio. The user picks a tab in the browser's share dialog and turns on tab audio. Offered only where `getDisplayMedia` exists and the device has no touch screen, which in practice means Chrome and Edge on a computer; Firefox and Safari have the API but pass no audio, and that case ends with a message. The video track is requested as small and slow as allowed and is not used.
- **mic**: `getUserMedia` with echo cancellation, noise suppression and automatic gain off, so the level follows the music.
- Both go through `startListening(mode)`: the stream becomes a `MediaStreamAudioSourceNode` into `cap.gain` (1 for a tab, 3 for a microphone), which feeds the analyser. `master.gain` is set to 0 while listening so the captured sound is never played back; a shared tab keeps playing from its own tab, and a microphone would feed back. `stopListening()` stops the tracks and restores the gain. A token (`cap.tok`) discards a stream that arrives after the music setting has changed. If the user stops sharing or the track ends, the mode falls back to off with a message. `liveAudio()` is true in these modes once a stream is connected, so the bands, overlays and the change detector work as for a file.
- **tap**: no sound. `tap()` averages the last few tap intervals; intervals under 0.36 s are doubled to keep pulses slow. The audio context is suspended so that music playing in another app is not interrupted.
- **off**: suspended as for tap.

The scrubber is a custom slider (pointer events with capture), not `<input type="range">`. The time label has a fixed width because a changing width was shifting the slider under the finger.

A select's `change` event may not count as a user gesture for audio on iOS, so a capture-phase `pointerdown` listener resumes the context on the next tap.

### Bands (`readMusic`)

| Band | FFT bins | Roughly | Drives |
|---|---|---|---|
| bass | 1–4 | below 200 Hz | motion zoom kicks, bloom, field of view, flight speed, Rings overlay |
| mid | 6–45 | 250 Hz–2 kHz | morph speed (Morph drifts), motion rotation and wobble, surface bands, Liquid filter, Spokes length |
| treble | 60–250 | above 2.5 kHz | specular highlights, colour fringing, hue drift, trail colour shift, Orbit lights |

Each band keeps a **level** and a **pulse** (`bandStep`). The raw average is normalised by a slowly decaying running maximum (so quiet and loud tracks both use the full range), a slow average is tracked, and the pulse is `max(pulse*exp(-5dt), clamp((x - avg)*gain))`, an onset detector with decay. Level follows with a fast attack and slow release.

In tap mode the bands are synthesised: bass on the beat, mids half a beat later, treble twice per beat.

With `prefers-reduced-motion`, all reactions are scaled to a quarter and several motions are disabled (`calm`).

### Change detector (`makeChangeDetector`)

Decides when the music has changed enough to justify a world change. Inputs each frame: energy `e = 0.5*bass + 0.35*mid + 0.15*treble` (raw, not normalised) and balance `(treble + 0.5*mid)/(bass + mid + treble)`.

It keeps a short average (time constant 0.8 s) and a long one (8 s) of each. Novelty is

```
|sE - lE| / max(sE, lE, 0.03) + 2.2 * |sB - lB|
```

and it fires when novelty exceeds 0.45, after a 5 s warm-up. After firing it holds for 4 s, during which the long averages are snapped to the short ones so the new sound becomes the baseline. `tools/unit.mjs` checks it against six synthetic signals. It has not been tuned on real music; the threshold 0.45 and the weight 2.2 are the two numbers to adjust.

### The song shapes the world (`js/song.js`)

With Morph set to "follows song" (`morph` 2 in `controls.js`, the default) the morph is not left to its clock: the music's fullness decides it.

**The tracker** (`makeSongTracker`, run by `songStep` from `readMusic` on the same energy `e` as the change detector). The analyser's bytes count in decibels (0 to 255 over 70 dB), so 0.1 of `e` is about 7 dB, and all the numbers here are in those units. It keeps a fast average `f` (0.5 s) and a slow one `s` (3 s), a full mark `hi` (jumps up to `s`, sinks toward it over 60 s, starts at `SONG_HI` 0.6) and a quiet mark `lo` (jumps down to `s`, rises toward it over 20 s, never nearer `hi` than `SONG_SPAN` 0.06, about 4 dB). `level = (s - lo) / (hi - lo)`, held in 0 to 1. Because `lo` rises quickly and may come within 4 dB of `hi`, a song whose verse is only a little under its chorus still runs from one end to the other; a song equally loud throughout sits at 1. Energy under `SONG_QUIET` is silence: the marks do not move, the level falls away, and music starting again is taken up from its first sound. A **drop** is `f - s > SONG_DROP` (0.08, about 6 dB) after 5 s of music, at most one every 8 s. `heard` holds `level`, `drop` (true for one frame) and `live`.

**From level to morph.** `denseSide(w)` measures a world once (cached by id): the open space (`de`, capped at a quarter of the period) at forty fixed places in one repeat, at three morphs each side of zero; the side with less is the dense one. A pack world, a cloud or a zoom gets the high end. `songMorph` gives `side * 0.85 * (2*level - 1)` plus a slow sway of 0.12, so a steady passage does not leave the world standing. In about half the worlds the morph changes the shape without making it measurably more or less open (Bulbs, Hive, Gates, Foam, Cell and others); there the two ends are still the two ends of the morph, but which is called dense is close to arbitrary.

**Steering.** The morph stays a function of `clock.morphT` (`morphValue`), so share spots and everything that reads it are unchanged. `tickClock` moves `morphT` with `morphSteer` toward the nearest time at which the morph's main wave `sin(0.09 t)` equals the aim, at no more than 3 clock seconds a second (1.2 with reduced motion) and slowing as it arrives. That is about the fastest the morph already went with loud mids, so the camera is no more likely to be overtaken by a surface than before. `morphT` is kept above zero by adding 200 pi, the time in which both of the morph's waves come round. Hold still does not call `tickClock`, so the shape stands; the tracker goes on listening.

**The drop.** `measure` in `flight.js` sets `cam.boost` to at least 0.6 on a drop (not with reduced motion, not while held still), the same soft surge an orb gives. A Journey template whose worlds change with the sound treats a drop as a change too (`stepJourney`).

**Tested.** `tools/unit.mjs` runs the tracker over the built-in song's energy bar by bar. Those 72 numbers were measured by rendering the song with `musicRender` into an `OfflineAudioContext` in headless Chrome and putting it through a copy of the analyser's arithmetic: the quiet opening and the breakdown come out near 0, the drops near 1, and drops are heard at bars 4, 17, 44 and 49. It also checks a steady song, a verse 4 dB under its chorus, silence, a start from silence, and the steering. Not tested: any real recording, a microphone (much quieter, so the first minute sits low until `hi` sinks), and how any of it looks in flight. `SONG_SPAN` and `SONG_DROP` are the two numbers to adjust.

## 11. Journey

### Clocks

`J` holds one clock per category: `world`, `palette`, `mirrors`, `motion`, `filter`, `overlay`, `surface`, `land`, `packing`, `pulse`, `shapes`, `inside`, `dance`. A dance option is `"any"` or a kind of dancing from `MV_STYLES` (js/moves.js), and matters only while an overlay with dancing figures shows. A packing option is a name from `PACKINGS` (`"grid"`, `"scattered"`, `"nested"`, `"sponge"`, `"helix"`, `"shells"`, `"descent"`), and shows only in the worlds it changes. A surface option is a name from `SURFACES` (`"plain"`, `"grain"`, `"dots"` and so on), and its off is plain. A land option is `"none"` or a landscape's `id` plus `" alone"` or `" over"`; templates saved before the land existed get `mode: "keep"`. `jReset(k)` sets the next firing time to `base * (0.8 + 0.4*random)`, so each change lands within a fifth either side of its target interval and the categories drift relative to each other.

### Templates

```js
{ name: "My trip", builtin: false,
  world:   { mode: "random", every: 55, set: null, trigger: "timer" },  // trigger: "timer" | "sound"
  palette: { mode: "random", every: 21, set: null },
  mirrors: { mode: "off",    every: 20, set: null, none: "even" },      // none: "even" | "50" | "75"
  motion:  { mode: "keep",   every: 24, set: ["Melt","Drift"] },
  filter:  { mode: "keep",   every: 27, set: null },
  overlay: { mode: "keep",   every: 22, set: null } }
```

- `mode`: `off` forces the category to none every frame; `keep` leaves it as the user set it; `random` changes it on the clock. Worlds, palettes, the packing, the pulse and the shapes have only `keep` and `random`.
- `set`: `null` means every option. Otherwise a list of option keys: world ids, palette names, mirror counts as strings (`"0"` is none), and motion, filter and overlay names. Keys are names rather than indices so templates survive options being added.
- `CATS` describes the categories and is what the engine and the editor both iterate over. `normT` fills in anything missing and drops unknown keys, so stored or pasted templates are always complete.

Engine functions: `jCur(k)` (current option key), `jPool(k, cfg)` (allowed options; locked palettes are excluded), `jPick(k, cfg, cur, pool)` (the next option; weighted for mirrors, otherwise uniform over the others), `jApply(k, key)` (apply it; returns false if a transition is running and it must be retried). The per-frame loop is in `frame()` inside `if (journey && started)`.

A world with `trigger: "sound"` changes when the detector fires and at least `max(10, every/4)` seconds have passed, or after `2.5 * every` seconds regardless. Without live audio it falls back to the clock.

Built-in templates: Classic, Everything, Clean flight, MilkDrop, Dance party, Kaleidoscope, Calm, Biomech, Visions, Landscapes, Follow the music. Dance party is MilkDrop's motions and some of its filters (not Echo, which lays a second, larger, upside-down picture of the figures over them) with the overlay held to the three with dancing figures (Dancer, Chorus line, Dance floor), changed every 40 seconds, and the kind of dancing changed every 60. Everything, MilkDrop and Follow the music change the surface at random; Clean flight holds it plain; the rest leave it as it is.

### Likes

`js/taste.js`. `taste` maps `"<category>:<option key>"` to a weight between `TASTE_MIN` (0.2) and `TASTE_MAX` (4); an option with no entry has weight 1. `jPick` chooses among the allowed options with `pickWeighted`, each in proportion to its weight (the weighted mirror choice still decides between none and some first). **More like this** (`jMore`) multiplies by 1.4 the weight of what is showing in every category the template sets to random. **Less like this** (`jLess`) multiplies by 0.6 the weight of what is showing in `jLast`, the category `stepJourney` changed most recently (or the first random category if it has changed nothing yet), and changes that category at once. A weight that returns to within 0.02 of 1 is dropped. The weights are in `localStorage["mirrorfold-taste"]`, read through `cleanTaste`; **Forget what I liked** in the setup panel empties them. They are not part of a pack. `tools/unit.mjs` checks the limits, the proportions and the cleaner.

### Sets

```js
{ name: "Grand tour", builtin: true, order: "cycle",   // or "random"
  items: [ { tpl: "Clean flight", min: 2 }, { tpl: "MilkDrop", min: 2 }, ... ] }
```

`advanceSet()` moves to the next item (or a random different one) when its minutes are up and calls `applyTemplate`. Items whose template no longer exists are skipped.

### Storage

`localStorage["mirrorfold-journeys"]` holds `{ tpls, sets, sel }`, where `sel` is `"t:<name>"` or `"s:<name>"`. Built-ins are defined in code and never stored. `adopt(raw)` validates stored or loaded data and skips names that collide with built-ins. It reads templates from `raw.templates` (packs) or `raw.tpls` (storage and older backups).

### Packs

A pack is JSON: `{ mirrorfold: 1, name, author, about, scene, palettes, motions, filters, overlays, worlds, templates, sets }`. The format and ranges are documented for authors in `packs/README.md`. Nothing in a pack is evaluated as JavaScript. The only code a pack can carry is the GLSL body of a filter or an overlay (below).

- **Cleaners.** `cleanName`, `cleanPalette`, `cleanMotion`, `cleanFilter`, `cleanOverlay` and `cleanCode` are pure functions. They refuse a wrong shape (returning `null`), copy only known fields into a new object, and clamp every number. The motion ranges are what keeps a pack from breaking the no-strobe rule, so widen them only after looking at the result.
- **Library.** Added palettes, motions, filters and overlays are appended to `PALETTES`, `MOTIONS`, `LOOKS` and `OVERLAYS` after the built-ins (`NPAL`, `NMOT`, `NLOOK` and `NOV` are the built-in counts) and stored in `localStorage["mirrorfold-library"]`. They are loaded before the selects and `CATS` are built. `libAdd` refuses built-in names, replaces an earlier added item of the same name, and stops at `LIB_MAX` (16) per kind.
- **Loading.** `loadPack(text)` is the one entry point for a file, pasted text and a published pack. It adds palettes and motions first, calls `refreshLists()` (which rebuilds the two selects and the palette and motion options in `CATS`), then adopts templates and sets, so a template can name items from its own pack.
- **The gallery** (`js/gallery.js`). `loadGallery()` fetches `packs/index.json` from the same folder as the page, once, when the panel opens, passes each line through `cleanEntry` (a file name matching `^[a-z0-9][a-z0-9_-]{0,60}\.json$`, a name, and optionally an author, a sentence and counts, all as plain text and small numbers) and shows a card for each with **Add**, which fetches the file and calls `loadPack(text, "site")`. Under `file:` it only says so. `packs/index.json` is written by `tools/gallery.mjs` from the pack files, and `tools/pack.mjs` fails if it is out of date.
- **Offering a pack.** The panel lists what may be offered, each with a tick box (`offerItems`, `offerFill`): the user's worlds, palettes, motions, filters, overlays, templates and sets from `packNow()`, less anything named in `fromGal`, and the scene showing now. `fromGal` is the names in every pack added with **Add** (`packNames`), kept in `localStorage["mirrorfold-from-gallery"]` and read back through `cleanFrom`; an item is known as the gallery's by its kind and name only, so a thing of the user's own given the same name later is left out too. **Offer what is ticked** builds a pack of the ticked things with `offerPick`, which also takes what they use if it is in the list (a set's templates; the options a template names in a `set`; the scene's world and look) and reports those so the message can name them. Nothing else is sent. It opens the repository's issue form (`.github/ISSUE_TEMPLATE/pack.yml`) with the pack in the address (`offerUrl`); past 6,000 characters the pack is left out of the address, copied, and the user pastes it. The repository is taken from the Help link, which `vr.js` already points at the right fork. On GitHub, `.github/workflows/offer.yml` runs `tools/offer.mjs` when an issue with the `pack` label is opened or edited: it reads the issue from the event file, runs every item through the cleaners (`tidy` in `tools/packlib.mjs`), and for a pack with anything left writes `packs/<name made here>.json` and the index, pushes the branch `pack/<issue number>` and opens a pull request. It comments on the issue either way. No step puts issue text into a command; the only values that reach the shell are the issue number and a file name of lower-case letters, digits and hyphens, which the shell step checks again. Nothing is in the gallery until a maintainer merges, and merging is what makes code `reviewed`. Untested on GitHub itself: the script was run by hand against made-up issues, and the workflow file has only been read.
- **A scene in a pack.** `cleanScene` checks an optional `scene`: a spot as Share spot writes it, the look by name, mirrors, FX and land. `loadPack` adds the library items first and then calls `goScene`, which looks each name up and passes over any it does not know. `sceneNow()` reads the current scene and `packOfScene()` wraps it with whichever of the palette, motion, filter, overlay and world in use are not built in.
- **Save picture** (`js/picture.js`). `pictureMake(fn)` asks for the next frame; `pictureFrame()`, the last step of `frame()`, calls `canvas.toBlob` while the frame is still on the canvas, and `pngPut` adds a `tEXt` part named `mirrorfold` holding `packOfScene()` as ASCII JSON (`asciiJson` writes every other character as `\uXXXX`). `loadFile` is the one way in for a file the user picks or drops: a PNG goes through `pngGet`, which checks every length against the file and stops at 200,000 characters, and then `loadPack` like any pack, so a picture can never mark code reviewed. Checked in headless Chrome: the file opens in other software with its text part, and loading it returns to the same scene. Untested: saving a file on a phone, where the download link may open the picture instead.
- **Palette locks.** `palOpen(i)` says whether a palette may be used: built-ins up to the orb count, and every added palette. Use it instead of comparing against `BASE_PALS + unlocked`.
- **Share links** store the palette by index in one base-36 digit. 13 built-ins plus 16 added fit. A link that names an added palette the receiver does not have keeps the receiver's current palette.
- **Filters.** A pack filter is a `LOOKS` entry: the same control fields the built-ins use (`edge`, `post`, `fx` and so on, clamped by `cleanFilter`) and optionally `code`.
- **Filter code.** `code` is the body of `void look(vec2 uv, inout vec3 col)`. `finalSource(code)` splices it into a copy of `FS_FINAL` with the helpers `scene`, `luma`, `aspect` and `pixel`, calls it after the built-in filter steps and before bloom, and clamps the result. `filterProg(lk)` compiles that copy on first use and caches it on the entry (`lk.prog`, `null` if it failed). Loading a pack compiles at once, so code that does not compile is left out; code restored from storage compiles when first selected.
- **What `cleanCode` enforces, and why.** No `#`, comments or backslashes, so the checker and the compiler see the same tokens. Balanced braces that never go negative, so the body cannot close `look` and define more functions (call chains of functions can multiply cost without any loop). No identifier matching `u[A-Z0-9_]…` or `gl_…` except `gl_FragCoord`, so the code cannot name the app's uniforms: it has no clock, no audio and no direct texture access. At most counted `for(int i=0;i<N;i++)` loops, with the product of the counts times the number of `scene` mentions at most 64, which bounds texture reads per pixel. No `discard`, which would leave pixels undefined.
- **Overlay code.** A pack overlay is an `OVERLAYS` entry `{ name, sound, code }`. `code` is the body of `void mark(vec2 p, inout float ln, inout float hue)`. `trailSource(code)` splices it into a copy of `FS_TRAIL` with the globals `time`, `beat`, `mid`, `hi`, `aspect` and the helper `sound(x)`, and runs it when `uOv` is 99. `overlayProg(ov)` compiles and caches it like `filterProg`. Unlike a filter, an overlay does get the clock and the sound, because an overlay without them is a still shape. `sound: "bands"` makes `updateWave()` fill the wave texture with the spectrum, as the built-in `spec` flag does.
- **Flash limiter.** For filters, having no clock is not enough: code can amplify tiny changes in the picture into a full-screen flip. Overlays have a clock outright. So while any code that is not marked `reviewed` is in use, pass 4 draws into `tF[fcur]` and blends with the previous finished frame (`uKeep = exp(-dt/0.25)`, sampler `uPrev`, both in the base `FS_FINAL`), then copies to the screen with `pCopy`. In real-time tests a filter written to flash swung more than 10% of full brightness 6 times a second with the limiter off and never with it on; an overlay written to flash, 12 times a second and never. `reviewed` is set only for packs fetched from the page's own `packs/` folder (`loadPack(text, "site")`) and is kept in `localStorage`; a file or pasted text can never set it. `tF` is allocated on first need and freed on resize.
- **VR.** Filters with code are treated as "none" while `stereo` is on, like the built-in filters that move pixels. Overlays are all off in VR already.
- **Editor.** `ED` describes the sliders for each kind (`p`, `m`, `f`): field, label, range and step. `edOpen(kind, i)` builds the sheet `#ed` and selects the item so the picture shows it. Every slider move runs `edRead()`, which builds an object from the sliders, passes it through the same cleaner a pack goes through, writes the result into the live item in place, and saves. So the editor cannot make anything a pack could not hold. `edNew(kind)` starts from a copy of what is showing (without any code). Renaming updates the names in the user's templates. Overlays have no editor. Each `ED` row also carries the help sentence that the **Help** button shows, so a control and its explanation stay together. The palette editor has plain controls on top of the twelve sliders: two colour pickers and the three `ED_SIMPLE` sliders. `palFromSimple` builds `a`, `b`, `c`, `d` from them (each channel swings between its value in the two colours; `c` is half the number of colour changes; `d` is the slide, plus a third of the rainbow setting per channel, plus a half where the channel runs downward). `palToSimple` reads the settings back from a palette and reports `exact: false` when the palette has no such settings; the editor then shows a note, because touching a plain control rebuilds the palette. The twelve sliders (**Fine tuning**) remain the source that `edRead()` reads. On a phone held sideways the sheet is a panel down the right side (a media query on `#ed`).
- **`tools/pack.mjs`** extracts the cleaners by name and fails on any pack in `packs/` that would be refused or changed. It runs on every push and pull request (`.github/workflows/check.yml`), together with `tools/unit.mjs`. `tools/check.py` loads every pack in `packs/` and fails if one does not load whole or a filter does not compile; it needs a browser and is run by hand.

### Setup panel

Built with a small `mk(tag, props, kids)` DOM helper. `advRenderT()` and `advRenderS()` re-render the whole template or set editor on each change, which is simple and fast enough at this size. Built-ins render read-only.

## 11a. Record flight

`js/flightdata.js` (free of the page) and `js/flightplay.js`. A flight is not a video. It is: the built-in song's seed (0 for none); the ids of the worlds visited; what was showing at the start and every change after, as `[seconds, kind, name]` with the kinds and names Journey uses (`jCur`, `jApply`); and the camera every `FL_DT` (0.5 s) as 15 bytes: its place as three parts of the world's period, turn, tilt and roll (16 bits each), the morph's clock within `FL_TURN` (200 pi, the time in which both of the morph's waves come round), and the world's number in the list. `flPack` makes the link's text: the header as JSON and the samples, each in URL-safe base 64, joined by a full stop. `FL_MAX` is 240 s, just under ten thousand letters.

**Recording** (`recFrame`, part of the frame step `flightFrame` after the camera has moved). Each frame it compares `jCur` of each kind with what it last saw and notes a change; a change made behind a transition happened at the transition's peak, so it is noted half a second earlier, when it was asked for, and so lands at the same moment played back. Time does not run while Hold still is on. With the built-in music `restartBuilt(seed)` starts a new song from a seed (`songRand` in `music.js` makes songs from the seed when there is one), and the seed goes in the link.

**Playing.** `flightPlay(text)` reads the link with `flUnpack`; a link in the page's address (`#flight=...`) waits until the start card is left. `beginPlay` turns Journey off, puts the first world in place, and restarts the song if there is a seed and the built-in music is on. `flightClock` (after the clocks) moves the flight's time on, hands due changes to `jApply` (those at time 0 with `now`, so the start is set up without three transitions in a row; one that finds a transition running waits, and those after wait behind it), and sets `clock.morphT`, so the world has the shape the path was flown through. `flightFrame` (after `move` and `stepZoom`) puts the camera at `flAt`: a Hermite curve through the samples' places, taking the short way where the world wraps, with the directions blended and squared up. A sample belongs to a world; around a change of world the camera is given only to the world the page is in, and otherwise left alone for those frames. Any movement key, stick or look by the user (`fr.idle`, `fr.mx`, `fr.my`, `fr.uz`, `cam.lookAct`) ends the playing where it is.

**Checked.** `flUnpack` refuses anything that is not a flight (length, letters, version, list sizes, name lengths, a sample naming a world not in its list); what comes through is numbers and names that are only compared with the app's own lists. Tested: `tools/unit.mjs` (samples, the curve across a wrap, packing, a list of broken links), and in headless Chrome a recorded straight flight played back from its link stayed within one frame's travel of the path, its changes landed on time, and a key press handed the controls back. Not tested: a real flight by Journey played back on another device; the song being the same to the ear. Limits: a zoom world's view, the land's own flight and a pack world are not recorded (the page shows them and lets them move by themselves); the sprites, the orb and everything the sound drives are made afresh, so they differ.

## 11d. Scores

A score is a journey made for a piece of music: an album's tracks, and for each the changes to make at given moments of it. It is the base of the composing mode for desktop browsers, which is being built in stages (the list is at the end of this section).

```js
{ name: "Album", tracks: [
  { name: "One", len: 200, marks: [30, 62.5],
    cues: [[0, "world", "julia"], [0, "journey", "Calm"], [40, "world", "temple"], [90, "journey", ""]] } ] }
```

A cue is `[seconds, kind, name]`. The kinds are Journey's thirteen (`SC_KINDS`), with Journey's names, and one more: `"journey"`, whose name is a template that makes changes by chance from then on, or `""` for none. So a passage can be left loose and a moment pinned, and the two mix: a template that keeps the world and changes the palette leaves the worlds to the cues. The flight is never in a score. Journey flies, so each playing is the same cues and a fresh flight. `marks` are the moments where the music changes, for the editor to snap to; playback does not read them.

**The cleaner** (`cleanScore`, `cleanTrack` in `js/scoredata.js`, free of the page). A score from a pack is a stranger's text. What comes out is times held inside the track's length and rounded to a hundredth, kinds from `SC_KINDS`, and names through `cleanName`, which are only ever compared with the app's own lists (`jApply`, `findT`). At most `SC_TRACKS` (40) tracks, `SC_CUES` (1500) cues and `SC_MARKS` (300) marks a track. Nothing may strobe: a cue of a kind within `SC_GAP` (1 s) of the one before it of that kind is dropped, and so is a cue that changes the picture at once (every kind but palette, dance and journey, `SC_SOFT`) within `SC_NEAR` (0.4 s) of another. Cues at time 0 are let through together, since they set the scene before anything is seen.

**Playing** (`scoreClock` in `js/scoreplay.js`, a step of `frame()` after `flightClock`). It runs only while Music is an audio file and a score is in use (`scoreSet`), and not under Hold still, a flown loop, a played flight or as a guest. The time is the file's own (`pPos`), so a pause holds the score. When the file changes, `scMatch` finds which track it is: the one of its length within `SC_NEAR_LEN` (1.5 s), then by name, then by place in the album; a file that is none of them leaves the score waiting. Going forward, cues are taken from `scOrder`'s list, in which a kind that is changed behind a transition (`SC_BEHIND`) is asked for `SC_LEAD` (0.5 s) early so that it lands on its moment, and handed to `jApply`; one that finds a transition running waits, and those after it wait behind it. When the time jumps (the start, the scrubber, the track gone round, Hold still let go), `scChase` gives each kind's last cue before that moment and they are made at once with nothing to cover them.

**A doorway for a cut.** A world's cue may have a fourth thing, `"door"` (`SC_CUTS`). It is then not asked for early: at its moment `doorOpen(i, true)` opens a doorway to that world, the autopilot steers into it, and the world changes on going through, some seconds later; if it is not gone through the world changes the old way when the doorway gives up. That is only done while Journey is flying; otherwise, and where there cannot be a doorway (a cloud, a zoom, the land, the VR viewer), the change is made behind a transition at once. After a jump in the music the world is simply set. **Transition or doorway** on the composing screen switches the chosen cue.

**Camera takes.** By default the flight is new each time. A track may also hold `takes`, passages where the camera's path is kept: `{t, w, d}`, the moment it begins, the ids of the worlds it passes through, and the camera every half second exactly as a recorded flight keeps it (`flSample`, 15 bytes), in the letters of a link. `cleanTake` checks the letters, that the bytes are whole samples (2 to 1202, ten minutes), that every sample names a world in its list, and that the take ends inside the track; at most `SC_TAKES` (24) a track, in order, and one that begins inside another is dropped. A track with none has no `takes` field. While the music is inside a take (`takeAt`), `scoreClock` sets the morph's clock to the recording's and `scoreFrame` (a step of `frame()` after `flightFrame`) puts the camera at `flAt`, as a played flight does; where the take was in another world than the one showing, the camera is left to Journey. Any steering hands over the controls until that take ends. A take is not flown while the camera is left-handed after a mirrored doorway. **Record the camera** on the composing screen starts one at the music's moment, sampled against the music's time whoever is flying, and a second press keeps it in place of any take it lies over; a jump in the music, the descent, a seventeenth world or ten minutes ends it. Takes are drawn as a Camera lane, and a chosen one is removed with Delete. The same limits as a recorded flight hold: a zoom world's view, the land's flight and a pack world are not kept.

**Journey's template.** While a score is in use it has the say over the template (`jUse` in `js/journey.js`): the one its last `"journey"` cue named, or `HOLD_T`, which changes nothing. A choice made in the Journey list meanwhile is kept for afterwards. `scoreSet` turns Journey on so that the autopilot flies; the user may turn it off and fly, and the cues are still made.

**An album.** The audio file chooser takes several files (`plGo`, `plSort` in `js/audio.js`). They play in the order of their names, numbers counted as numbers, and after the last comes the first. There is a short silence between tracks while the next is decoded.

**Kept and passed on.** `localStorage["mirrorfold-scores"]` holds `{list, sel}`, read through `cleanScore`; at most `SCORES_MAX` (24). A pack may hold `scores` (at most 4 in the gallery): `loadPack` hands them to `scoresAdopt`, and `packNow` writes the user's. The **Score** button beside the audio file's controls takes each score in turn, then none; it is hidden while there are none.

**Hearing a file ahead** (`js/scoreanalyse.js`, free of the page). The app hears music one frame at a time through the browser's `AnalyserNode`. To hear a whole file before it is played, `anStep` does the analyser's arithmetic itself: 1024 samples ending at each sixtieth of a second, Blackman's window, the spectrum (`anFft`), magnitudes divided by 1024, smoothed by `AN_SMOOTH` (0.6, the number `ensureAudio` sets), and counted 0 to 255 over -100 to -30 decibels. Each frame's bins then go to the listeners the app itself uses while it plays: the three bands and the energy of `readMusic`, `makeChangeDetector`, `makeSongTracker` and, through `onsetStep`, `makeBeatBank`. So what a draft is made from is what the picture will do when the music plays. `anDone` gives the length, the energy and the fullness as curves of `AN_HZ` (5) numbers a second, the beats that were sure, and `marks`: each firing of the detector and each drop, set back to where the change itself was (`sharpest`: within the 2.5 s before it was noticed, the moment with the greatest difference between the 0.4 s after and the 0.4 s before). The beats give the tempo but may lie a part of a beat off the drum, so marks are not moved to them. It takes about a third of a second for a minute of music.

**The draft** (`scDraft`). The track is cut at its marks into sections no shorter than `DRAFT_GAP` (14 s), a drop being kept in preference to a change beside it, with nothing in the first 4 s or the last 7. A section is quiet, middling or full by the mean of its fullness (`draftTier`: under 0.35, under 0.7, above), is given that tier's template as a `"journey"` cue, and begins in a new world on its moment, taken by chance from that template's worlds and never one of the last two, across tracks as well. **Draft a score** (`draftAlbum` in `js/scoremake.js`, beside the audio file's controls) does this for every file chosen, with `DRAFT_TPL` (Calm, Classic, MilkDrop), keeps the score and puts it in use. `hearFile` decodes one file at a time with `decodeAudioData`, mixes it to one channel, and listens in slices of 12 ms between frames; a second press gives up. A file over `HEAR_MAX_SEC` (25 minutes) or `HEAR_MAX_BYTES` is not heard ahead, since decoded whole it would not fit in memory: its track is left to the middling template. What was heard is kept by file name and size while the page is open (`heardFile`), for the composing screen.

**The composing screen** (`js/studio.js`, the **Compose** button, which is hidden on a touch screen or in a window under 900 pixels wide). `setStudio` shows the panel `#studio` along the bottom and gives the picture the room above it (`body.studio` in the stylesheet, then `resize()`). The panel is a row of buttons and one 2D canvas, drawn every frame by `studioFrame`, the last step of `frame()`: a ruler, the playing track's music as `heardFile` has it (loudness as bars, fullness as a line; a track not yet heard is listened to once, in the background), the marks as dashed lines, and a lane for each kind that has a cue (By chance, World and Palette always), each cue a block that lasts until the next of its kind.

A score is made mostly by doing. While **Keep my changes** is on, `studioFrame` compares `jCur` of each kind with what it was at the last frame, and a change that neither the score asked for (`scMade` in `js/scoreplay.js`) nor Journey chose (`jMade` in `js/journey.js`) is the user's: it is written as a cue at the music's moment (`pPos`), playing or paused. So the app's own controls, keys and a MIDI box are the tools, placing one change exactly and playing along live are the same act, and a change made behind a transition is written at the moment it lands. The template for a passage is set from the list in the panel. A click on the ruler or the music moves the music (`pSeek`), and `scoreClock` then shows what the score asks for there; Shift and a drag marks a passage that is played round and round. A cue is dragged to another moment, catching on a mark within 8 pixels unless Alt is held, or removed with Delete. Two presses in a lane write what is showing now. The wheel zooms about the mouse (`stZoom`), and with Shift moves along. Enter plays and pauses; Ctrl+Z and Ctrl+Y undo and do again (`ST_UNDO`, 100 states a track, kept while the page is open).

Every change goes through `edit`, which hands copies of the track's cues and marks to `scoreEdit`, and so through `cleanTrack`. `stPut` places a cue so that the cleaner will let it stand: a cue of its kind within `SC_GAP` gives way to it, and if a cue of another kind that changes the picture at once is within `SC_NEAR` the new one goes just after that. After an edit `scoreClock` chases, which changes only what now differs. **Save as a pack file** writes the score and the user's templates it names. **Start empty** listens to the files and makes a score with marks and no cues.

**Tested.** `tools/unit.mjs`: the cleaner on good, broken and too-fast scores, the early asking, the chase, the matching. `tools/check.py`: a score loaded from a pack makes its changes at the right moments of a stood-in file, forward and after a jump back. Also in `tools/unit.mjs`: a made-up ninety seconds (quiet, thirty seconds with a kick drum, quiet) is heard with its drop and its breakdown marked within a quarter of a second, its beat at the right tempo, and drafted as three sections under the right templates. By hand in headless Chrome: two WAV files made in the page were decoded, heard and drafted into a two-track score, and on the composing screen at 1280 by 800 a palette and a filter changed by hand were written at the paused moment, undone and done again, a template set, a cue removed and the score renamed; the screen was looked at as a picture. `tools/check.py` also records a camera take over four seconds of a stood-in file, flies it again and hands over on steering. `tools/unit.mjs` has the timeline's arithmetic (`stZoom`, `stSnap`, `stPut`, `stLanes`), and `tools/check.py` writes a change by hand and undoes it. Not tested: the mouse on the timeline (dragging, the wheel, the loop), a MIDI box, a real browser window. Not tested: any real recording (the detector's and the tracker's numbers have never been tuned on one), a real album played through, the gap between tracks, a score on a phone.

**Still to build**, in this order: (4) a blink of the eye as a cut; drawn curves for the morph, the speed and the FX; (5) matching someone else's copy of an album by its energy curve, and following a streamed tab; (6) drawing a score to a video file frame by frame, faster or slower than real time. Also wanted on the composing screen: pictures of the worlds and palettes to drag onto a lane, marks that can be added and moved by hand, editing a track that is not the one playing, and the whole album on one ruler. Scores are not yet in the list of things that can be offered to the gallery.

## 11b. Fly together

`js/together.js` and `server/rooms.js`. Two to four pages joined by WebRTC data channels. **Introducing them** takes a meeting point, because two browsers cannot find each other unaided: each must first be handed the other's session description. The meeting point is `server/rooms.js`, a Cloudflare Worker with one Durable Object per room, at the address in `TG_ROOMS` (empty: Invite says there is none). It carries the two descriptions and nothing else.

- *Host.* `tgInvite` makes a room code (eight of `TG_LETTERS`) and a secret key, opens a WebSocket to `/room/<code>?role=host&key=<key>` (`tgRoomOpen`) and copies the link `#room=<code>`. The socket stays open while the invitation stands; `tgPing` says `p` every 25 seconds and the room answers `q` without waking. If it breaks it is reopened up to five times, each after a longer wait, and the key lets the same page take its room back. Friends already joined do not depend on it.
- *Guest.* `tgJoin` makes an `RTCPeerConnection`, the data channel and a receive-only audio line, waits up to four seconds for the browser to gather its addresses, opens `/room/<code>?role=guest` and sends `{t: "o", s}`. The room passes it to the host as `{t: "o", g, s}` with a name `g` for that guest; the host (`tgAdmit`) answers `{t: "a", g, s}`, or `{t: "n", g}` when all `TG_MAX` places are taken, and the room hands the guest `{t: "a", s}` or `{t: "n"}` and lets it go. A guest still waiting when the host leaves is sent `{t: "e"}`.
- *Checks on the page.* Everything from the room goes through `tgSignal`: only those kinds, a name of at most 16 small letters and digits, a description of at most 10,000 letters that starts `v=0`. The description goes nowhere but to `setRemoteDescription`. A code from a link goes through `tgRoom`.
- *Checks in the room.* Only pages from `ORIGINS` (`server/wrangler.toml`); thirty connections a minute from one address (counted per running copy of the script, so it is rough); a guest may send one message, has a minute, and at most six wait at once; a room lasts twelve hours; no message over 12,000 letters. Refusals are WebSocket closing codes the page turns into sentences: 4404 no host, 4408 out of time, 4409 another host has the room, 4429 too many waiting.
- *Failing in the open.* `tgWatch` gives each joining `TG_WAIT` (30) seconds and ends it at once if the connection's state becomes `failed`; `tgFail` then says which half failed, the meeting point or the direct connection. `TG_ICE` names two public STUN servers (Google's and Cloudflare's), asked only for the page's outside address while a description is made. There are two so that the connection report can compare what they saw. There is no relay, by choice (a relay carries the music and is charged by volume), so two people of whom one is behind a strict router cannot connect.

**Messages**, every `TG_EVERY` (0.1 s), as JSON through `tgClean`, which lets through only numbers in range and names of at most 40 letters. A guest sends `{w, q}`: its world's id and its place as parts of the period. The host sends each guest `{w, mt, o}`: the host's world, its morph clock, and everyone else as `[number, world, three parts]` (the host is 0). So the host relays, and guests are not connected to each other.

**The host's world is everyone's.** `togetherClock` (a frame step after the clocks): a guest whose world differs asks for the host's (built-ins only, looked up by id) and eases `clock.morphT` to the host's, the short way round `TG_TURN`, so all fly through the same shapes; its own Morph setting is overridden while joined, and `stepJourney` leaves the choice of world alone (`tgGuest`). The host's messages also name everything else Journey changes (`TG_KINDS`: `pa` palette, `lk` filter, `mi` mirrors, `mo` motion, `ov` overlay, `sf` surface, `ld` land, each from `jCur`); a guest hands each to `jApply` when the name differs from the last one taken up (`hostHas`), and notes it only when `jApply` says it started, so a change refused because a transition was running is tried again at the next message. A guest's own choice lasts until the host's next change of that kind, and a name the guest's page does not have (one from a pack) is passed over. `stepJourney` changes nothing on a guest. Only the flight stays each person's own.

**Going to a friend's spot.** Five words travel on the same channel as `{c, ...}` (`TG_ASKS`), through `tgClean` like every other message: `come` (come to me), `join` (may I come to you), `coming` (yes to come), `here` (my place: the world, three parts of the repeat, the facing and up directions), `no`. A guest's word goes to the host, which adds who it is from (`f`, the guest's number, never taken from the guest's own text) and passes it to whoever it is for (`to`, or everyone). `tgAsked` only ever shows a request (`ask`, with Yes and No in the row for `TG_ASK` seconds). The camera is moved in one place, `tgGoTo`, on a `here`, and only while `want` says this page is waiting for one from that person: after its own user pressed **Go to my friend**, or pressed yes to a `come`. So no message can move a camera whose user has not just agreed. `tgSpot` turns the place into a camera, and it is refused if the world differs, the world has no places (zoom, pack) or a recorded flight is playing.

**The host's music.** `tgTap` connects the analyser's output through a gain to a `MediaStreamAudioDestinationNode`. The guest's description asks for one audio line, receive-only, and `tgAdmit` puts that stream's track on it before answering, so nothing is renegotiated later. What the analyser hears is what is sent: the built-in music, a file, a shared tab. The gain is shut while the source is the microphone. `tgMusicSdp` adds `stereo=1;sprop-stereo=1;maxaveragebitrate=128000` to the Opus line of each side's own description (`tgSetLocal`, which falls back to the description as made if the browser refuses it), since the default is tuned for speech in one channel. On the guest, `ontrack` hands the stream to `setFriendSound` in `listen.js`: the Music list gains "Host's music" (`musicMode` `"friend"`), chosen at once; `friendPlay` connects the stream to `bus`, so it is heard and the analyser, the bands and the song tracker all follow it, and also gives it to a muted audio element, because Chrome feeds a stream from another browser to the audio graph only while something plays it. Leaving removes the option and turns the music off. Sound goes one way, host to guests.

**Drawing.** `stepTogether` (after the sprites) fills `peerU`, three places and sizes for the scene shader's `uPe`: each person heard from in the last `TG_GONE` seconds and in this world, eased toward their last place (`tgPlace`, the short way round the wrap) and drawn at the copy nearest the camera, size 0.16 of the open space round the camera. The shader's `friend()` draws a ring with a dot at its middle, in a palette colour, hidden by anything nearer. Not drawn in a zoom or pack world. Under Hold still they stay where they were drawn.

**Tested.** `tools/unit.mjs`: the message, room-code and meeting-point checks against lists of broken input, the placing, the shader's line count, and that page and room agree on what a code is. `server/test.mjs` checks the room's rules against a local copy (`npx wrangler dev`): 17 cases, among them another site refused, a second host turned away, the same host taking its room back, one message per guest, six waiting at most. In headless Chrome, through that local copy: the page as host opened a room, a second connection in the same page joined through it, the channel opened, the guest received an audio track, places arrived and were drawn where expected, the room stayed open after the guest left and closed on Leave; and the page as guest was turned away from a room with no host with the right sentence, then joined a room hosted by a second connection sending a tone, took the host's palette and filter, switched to Host's music with the sound graph running, and went back to no music when the host left. The same 17 cases pass against the script on Cloudflare. In headless Chrome with stand-in channels: a guest took up the host's palette, filter, motion and overlay at once and the kinds that go behind a transition one after another; a place nobody agreed to, and one from the wrong person, moved nothing; yes to a call sent `coming` and the place that followed was gone to; the host passed a guest's request and a guest's place on to the right people with the right number and did not act on what was not for it. Not tested: a page on the site joining through it, the requests between two real devices, whether the music is actually heard and how it sounds, the delay, two real devices, two networks, three or more people, a phone, a host whose tab is in the background for a long time.

**A host whose page was asleep.** A phone stops a page that is not in front, and a host on a phone has to leave the page to send the link. Its connection to the room then looks open at Cloudflare and hears nothing, so a guest's description went nowhere and the guest gave up after `TG_WAIT`. (Found from the first connection reports: the guest was healthy and heard nothing; the host's page was hidden for 35 seconds.) Now: when the host's page shows again it takes its room afresh at once (`visibilitychange`, then `tgRoomOpen`); the room, on a host taking it again, tells every waiting guest `{t:"h"}` and lets each send once more; the guest sends its description again; and `tgAdmit` drops an unfinished connection to the same guest before starting another. A guest waits `TG_WAIT_HOST` (170) seconds for the host's description, inside the room's three minutes for a guest, and `TG_WAIT` from then for the connection itself. An older page ignores `h`, and a newer page works with an older room as before. Tested: the room's part against a local copy (`server/test.mjs`), `tgSignal` in `tools/unit.mjs`; the page's part not at all between real devices.

**The connection report** (`tgLog`, `tgDebug`, the **Copy connection report** button, and the console under `[fly together]`). Every connection is watched from the moment it is made: each way of being reached that the browser finds (`host`, an address on the device; `srflx`, the address a STUN server saw; with protocol, port, the server it came from where the browser says, and the address shortened by `tgAddr`), any STUN error, each change of gathering, ICE, connection and signalling state, what the other side's description offers (`tgCands`), the meeting point's opens and closes with their codes, and, when ICE connects or fails, how many candidate pairs ended in each state and which pair is in use (`getStats`). On a failure `tgVerdict` names the likeliest cause: a side with no `srflx` (UDP blocked, or the STUN servers unreachable), or a side whose two STUN servers saw the same address with different ports (`tgSplit`: a symmetric NAT, which gives every destination its own port, so the port a friend is told is not the one their packets must go to; nothing but a relay gets through that). The report is cleared when a room is opened or joined. Tested: the readers and the verdict in `tools/unit.mjs`; in headless Chrome only that the listeners attach and the lines appear, since connections do not progress under virtual time. Never run across two real networks.

## 11c. Doorways

`js/doors.js`, with the drawing in `js/render.js` and `js/shaders.js`. A doorway is a ring in one world with another world showing through it, and flying through it changes world with no cut. It is a real opening, not a picture of one: what is seen through it is what is seen after going through.

**The mapping.** A doorway joins a place `p` in the world in use to a place `q` in the other, with one facing `n` for both ends and a scale `s`. A camera at `p + x` sees through the ring what a camera at `q + s*x` in the other world sees, facing the same way. Since a view from a point does not change when everything is scaled about that point, the scale changes nothing in the picture; it only matches the sizes of the two open spaces, so that the ring fits both.

**Placing** (`doorPlace`, tried every frame for up to `DOOR_TRY` seconds). `doorAhead` walks the world's JavaScript `de` straight ahead and four ways a little to the side until something is in the way, and puts the ring part of the way along the clearest: at most 0.45 of the open space there and 0.3 of its distance from the camera, facing the camera, and within 0.4 of the period so that its nearest copy is never in doubt. `doorSpot` takes the most open of 160 chance places in the other world's period (at the same morph) and a ring 0.45 of the space there; `s` is the ratio of the two rings. Both need a `de`, which is why zoom, cloud and pack worlds have no doorways.

**Drawing.** Each frame `doorView` gives `drawScene` the other world, the camera's place in it, the ring's place in it and the part of the picture the ring can show in (`doorBox`, a rectangle round the ring's bounding ball; all of it when the camera is near the ring or mirrors are on). `worldPass`, which draws any world from any place, is run for the other world into `tD` (`doorTarget`, the size of `tA`) with the scissor set to that rectangle, so a small far ring costs little. It is run with `uDoorC` set: the ray starts at the ring's plane, so nothing between the mapped camera and the ring is drawn, and with no orb, sprites, friends or doorway of its own. Then `worldPass` draws the world in use with `uDoor` (the ring's middle, at the copy nearest the camera, and its size now), `uDoorN` and `uDoorT`: a ray that meets the ring's disc before any surface shows the rim, and inside it `thru` is set and the pixel is taken from `tD` at the same place in the picture, after the shader's own finishing, since `tD` is already finished. Everything else that goes into both passes (the clock, the sound, the palette, the morph, the mirrors, the jitter of Hold still) is the same, which is what makes the two agree.

**Going through** (`stepDoor`, after `move`). The camera's place from the ring's middle is kept from frame to frame; when it changes side within the ring (`doorCross`), `doorThrough` calls `setWorldNow`, puts the camera at `q + s*x` with its velocity scaled, corrects the frame's notes (`w`, `per`, `dist`) for the steps that follow, and leaves the mirror-image doorway behind as the way back for `DOOR_BACK` seconds (`DOOR_BACK_J` while Journey is flying). A frame in which the camera was wrapped by the period is skipped.

**Closing.** After `DOOR_LIFE` seconds, when the autopilot has passed it, or when the morph has brought a surface within 1.2 ring sizes of either end (measured three times a second). It shrinks before it goes. A doorway Journey opened then asks for the world the old way (`requestWorld`), so Journey always moves on. It is dropped at once if the world changes some other way, or the land, the VR viewer, a recorded flight or being a guest comes on.

**Journey.** `stepJourney` hands a due change of world to `doorOpen(i, true)` when `doorsOn` and Movement is travel; `doorSteer` turns toward the ring's middle. While the straight way to the ring is clear (`doorClear`, four places along it) it returns true and `frame()` leaves `autopilot` out, so nothing pulls the flight off the ring; if something is in the way it only leans toward the ring and the autopilot steers too. Behind Journey's flight the way back closes after `DOOR_BACK_J` seconds, not `DOOR_BACK`, so the autopilot cannot turn round and go back through. `stepJourney` starts the world's clock again whenever the world in use changes, however that came about (a doorway is asked for well before it is gone through), asks for no world while a doorway of its own stands (`doorOwed`) or a transition runs, and passes over the world just left (`jFrom`) when there is another to pick. In eight pairs of worlds, three flights each, driven frame by frame in headless Chrome, every flight went through within a tenth of the ring's size of its middle, in two to four seconds.

**Strange doorways** (`doorOpenLie(kind)`, `DOOR_LIES`). The same machinery with both ends in one world. The mapping gains a turn `T` (nine numbers, or null): a camera at `p + x` sees what one at `q + s*T*x` sees with its own directions turned by `T`, and `doorThrough` turns the camera's directions and velocity by `T` as it goes through, so the picture does not change. `worldPass` takes the turn and draws the far side with the turned directions. Every `T` leaves `n` as it is, so the ring, its clip plane and `doorCross` need nothing new. *Small*: `T` is nothing, and `doorSmall` walks `de` straight on from the ring to where the room is just enough for a ring `DOOR_SMALL` (0.12) of the size; `s` comes out near 0.13, and the camera arrives close to the surface, where the speed rule slows it by itself. Journey is given a turn toward the side with most room as it arrives, or it creeps up to the wall it faces. If nothing is within one and a half periods straight ahead for 1.5 seconds it becomes one of the other kinds. *Over*: `q = p`, `s = 1`, `T` half a turn about `n`. *Mirror*: `q = p`, `s = 1`, `T` a reflection in the plane through `n` and up. A mirror's `T` has determinant -1, so after it the camera's right is the other way round from up and forward: `cam.hand` is -1, `camSquare` builds right from up and forward with it, and `turn` reverses each turn about its axis so that right on the screen stays right. `placeCam` sets it back to 1 (any change of world but an ordinary doorway, which keeps it so that nothing flips at the ring), and so does the VR viewer. The way back is the same doorway with `T` undone (`doorUnturn`). Journey opens one every `LIE_EVERY` (70) seconds of flying, give or take a third, while `doorsOn` and not `calm`. Not allowed while a flight is being recorded: a flight keeps the camera's path and not the doorways, and would play the turn as a lurch.

**What is not carried through.** Friends flying together follow the host by the old transition. A recorded flight replays a doorway as a change of world behind a transition. The VR viewer and the land have no doorways.

**Tested.** `tools/unit.mjs`: placing against a made-up world, the far end, going through and missing, the picture's part, and that the uniforms are asked for. In headless Chrome: pictures of a ring in two worlds looked at; a picture taken just before the ring and one just after going through show the same scene; Journey's autopilot through four pairs. Not tested: a real chip, real flight, frame rate.

## 12. Orbs and share links

**Orbs.** `spawnOrb()` samples 260 random points in one period and scores them by distance from surfaces and from the camera. The orb's radius scales with the open space around it. Every 1.5 s the orb is checked against the morphing surface and respawned if swallowed. The first six orbs unlock palettes; later ones trigger a world change. The Orbs button hides them and is remembered in `localStorage["mirrorfold-orbs"]`.

### VR viewer

`setStereo(on)` switches a side-by-side stereo mode for a phone in a Cardboard-style viewer. The button is hidden on devices without touch; the harness can still call `setStereo(true)`.

**Rays.** The scene shader takes `uVr = (on, lens centre offset in buffer pixels, tangent per buffer pixel, half the eye spacing in world units)`. A pixel in the left half of the buffer belongs to the left eye. Its position relative to that eye's lens centre, times the tangent per pixel, is `q`, the tangent of its angle as seen without a lens. The lens is modelled with Cardboard's radial polynomial, `uv = q * (1 + 0.34*|q|^2 + 0.55*|q|^4)`, and the ray is `normalize(uCam * vec3(uv, 1.0))`. Because each pixel's ray is bent the way the lens will bend its light, no separate distortion pass is needed. Pixels with `|uv| > 1.8` are black and are not marched. The ray origin is `uPos + uCam * vec3(eo, 0)` with `eo = (-half, 0)` or `(+half, 0)`.

**Geometry.** Lens spacing is 64 mm and lens-to-screen distance 39 mm (Cardboard V2). The browser does not expose physical screen size, so one CSS pixel is assumed to be 0.162 mm. This is the main source of error and has no user adjustment yet. `uPix` is set to the tangent per pixel so the hit threshold still tracks pixel size.

**Eye spacing.** `vrEye` eases toward `0.021 * dist`, where `dist` is the distance to the nearest surface. That is a 64 mm spacing in a world scaled so the nearest surface is about 1.5 m away. It follows the same idea as flight speed: the world keeps a similar apparent size however deep you fly. Volumetric worlds report a constant distance of 0.2.

**Mirrors.** The fold acts on the ray direction, as in normal mode. For the angle `a0 = atan(uv) + uSpin`, the fold is either a rotation or a reflection of the plane, depending on the wedge. The same rotation or reflection is applied to `eo`. Both eyes' rays through one wedge are then moved by one rigid transform, so depth is consistent inside each wedge.

**Head look.** `onGyro` handles `deviceorientation`. `devMat(alpha, beta, gamma, o)` builds the W3C rotation matrix `Rz(alpha) Rx(beta) Ry(gamma)` and multiplies it by `Rz(-o)`, where `o` is the screen rotation, giving screen axes in earth axes. Working with matrices avoids the jump in the angles when gamma passes 90 degrees, which is where a phone in a viewer sits. `gyroTurn(P, S)` returns the rotation between the previous and current matrix as an axis-angle vector in screen axes (x right, y up, z toward the viewer). That turn is applied to `R`, `Up` and `F` about `-x*R - y*Up + z*F`; the signs differ because the camera's forward axis points into the screen. Only the change between events is used, so the head turn adds to touch look and to the autopilot's steering, and the compass heading does not matter. Turns over 0.6 radians between events are dropped. iOS needs `DeviceOrientationEvent.requestPermission()` from a tap, which the button's click provides.

**Comfort.** While `stereo` is true `jPool` leaves the cloud worlds out of Journey's choice of world (they have no surfaces, so both eyes see the same flat glow), unless a template allows nothing else, and `autopilot` turns at half its usual rate. Both were chosen by reasoning; neither has been tried in a viewer.

**Effects in depth.** An effect worked out on the screen shows each eye something different. A user with a real viewer asked for the motions, filters and overlays there, so the two effect passes have a second way of working (`VR_GLSL` in `js/shaders.js`).

- *The middle view.* Take an eye midway between the two. It sees a point at depth `z` (along the way the head faces) at `c`, the tangents of its angles. The left eye sees it at `c + eta` and the right at `c - eta` (in x only), where `eta = h/z` and `h` is half the eye spacing. In code, `e = c - side*eta` with `side` -1 for the left half.
- *Depth in the picture.* In the viewer the scene shader writes `eta/0.064` into the fourth number of each pixel (`eta = uVr.w * sqrt(1+|uv|^2) / t` for a hit, 0 for no hit, a cloud world or a zoom world). Outside the viewer it writes 1, as before. The trail pass passes it on: where the trail is brighter than the scene it keeps the trail's, else the scene's.
- *The lens.* `eyeOf(tc)` turns a place in the picture into `e` for that half's lens, with the same fifth-degree curve the scene shader uses. `texOf(e)` goes back: four steps of Newton's method on `r(1 + 0.34r^2 + 0.55r^4) = |e|`, then kept inside that eye's half.
- *An effect is a bend of the middle view that carries depth.* Each effect was already a function from a place to the place it reads from. In the viewer it is given `c*0.55` (so the edge of what the lens shows is about 0.5, the range the effects' numbers were made for, with the aspect taken as 1) and what it returns is read at `F(c) + side*eta_src` in the same eye's half. `eta_src` is the depth of what is read, which is not known until it is read, so the pass guesses, reads, and does it once more.
- *Trails* (`FS_TRAIL`) are the exception: they do not carry depth, they are painted on the world. The middle view of the surface point at this pixel (`c = e + side*eta`, with this pixel's own `eta`, so exact) is turned by `uTurn` and bent by the motion; the place that gives is read in this eye's half at the depth of what lies there (guess this pixel's, read, read again). Both eyes therefore see the same trail colour on the same surface point, and the pass writes the scene's depth on. The first version carried the trail's own depth and divided it by the zoom, so Tunnel's trails came toward the viewer; a user with a real viewer said motions then looked like a separate layer over the world, not the world changing, which is what they look like outside the viewer. `uTurn` is last frame's camera axes dotted with this frame's, so a trail stays where it is in the world while the head turns. Only turning is undone, not travel.
- *Filters and transitions* (`FS_FINAL`, `uVr = 2`). The loop round the bending code runs twice: once from the depth of what is at this pixel, once from the depth of what the first bend brought. Every read of the picture goes through `at()`. `uVr = 1` is the viewer with nothing bending the picture (no filter that moves pixels, no transition under way, no colour fringing): the picture is shown as it is, with no resampling.
- *Overlays.* Drawn in the middle view. Their base depth is `uOvEta = 1.25 * vrEye/dist * (1 + 0.2*beat)`, at most 0.05: a little in front of the nearest surface. Each part is at `uOvEta * ovDepth(d)`: for Ring and Scope `1 + 0.5*wave`; for Spectrum, Spokes, Rings and Spiral `0.3 + 2*radius` (a cone, near at the rim); Orbit's lights each at `1 + 0.6*sin(...)` of their own; a pack overlay and the dancers flat. Where a part is seen depends on its depth and its depth on where it is, so the place is worked out three times. Where an overlay is drawn its depth is written, so the filters move it rightly; its trails fall on the world like any other. The first version was one flat plane, which a user with a real viewer found flat. Echo's second copy is read at its own depth and laid on what is at the pixel.
- *Left as it was.* A pack filter's code is not run in the viewer (it is written for the screen). CRT, Halftone and Tape's grain take their pattern from `gl_FragCoord`, so the pattern is not at any one depth. Bloom is blurred across the whole picture, so a little crosses between the eyes at the middle. Flat video is off. The idle roll is skipped. Field-of-view pulsing does not apply because the lens model fixes the field of view.
- *The land.* `ray()` in the land shader has the same per-eye lens and the same turn of the eye's place under mirrors as the scene shader, and sets `gEo` (the eye beside the camera), `gR2` and `gPix` (the tangent one pixel covers there, which the lens makes up to five times larger at the rim; the coarse first pass and the city's pattern fade use it). The ray starts at `uPos.y` plus `uCam * (gEo, 0)`. Half the eye spacing is `landEye`, eased toward 0.021 times the height above the ground in `moveLand`: the land and a world behind it each have their own, which is right, since their sizes have nothing to do with each other and `eta` is an angle. Alone, the land writes `eta/0.064` as the scene shader does. Over a world the fourth number must also say where the land is, so it is 0 for none and `0.5 + 0.5*eta/0.064` for land; `FS_MIX` turns that back into a picture carrying the depth of whichever is seen, and the world shader leaves out pixels where it is over 0.3. That costs the thinning of far land into the world. `landFx` is taken as 0 (the effects need the one mixed picture). `mirrorOf` and a lake show the sky: their look-up of the world is by screen position, which differs for each eye. The lens numbers (`fr.vrOff`, `fr.vrTan`) are set at the top of `drawScene`, before the land, because the effect passes divide by them whatever was drawn; set only where a world is drawn, land alone with trails on went black.
- *Checked how.* `tools/stereo.py` matches blocks of the left half against the right and reports the shift. For the plain picture and for Twirl, Quad, Tiles, Mosaic, Liquid, Vortex, Tunnel, Melt with Ring, and Rings, the up-and-down shift averaged 0.3 to 0.5 pixels with none over 1 pixel: the same as the plain picture. A transition half way through had 6% of blocks over 1 pixel. The land alone (five landscapes), over a world, and with motions, a filter, an overlay and mirrors gave the same or better (0 to 0.5 pixels; the steel ball over a world 4% over 1 pixel, and it is a mirror, which truly shows each eye something different). That test is at 500 pixels an eye, where depth is only a few pixels, so it shows the two pictures agree but not how it feels. Not seen in a viewer. The cost on a phone (up to a dozen extra lens inversions a pixel) is not measured.

**Screen wake.** `keepAwake()` holds a screen wake lock (`navigator.wakeLock`) while Journey or the VR viewer is on, since nobody touches the screen then. `setJourney` and `setStereo` call it. The browser drops the lock when the page is hidden, so it is taken again when the page becomes visible. Browsers without the API, and iOS before 16.4, fall back to the phone's own lock timer.

## 14. Testing

There is no test framework. `tools/` holds what was used during development:

| Command | What it does |
|---|---|
| `node tools/unit.mjs` | Imports the pure functions (change detector, picker, head-turn math, steering handoff, cleaners, palette conversions) from the modules and tests them |
| `node tools/pack.mjs` | Checks every pack with the app's own cleaners, and that `packs/index.json` is up to date |
| `node tools/gallery.mjs` | Writes `packs/index.json` from the pack files |
| `node tools/offer.mjs event.json --dry` | Runs the gallery's offer check on a saved issue event |
| `python3 tools/probe.py` | Compares every world's GLSL `map` with its JavaScript `de` through the distance probe |
| `python3 tools/check.py` | Headless smoke test: compiles all worlds, cycles every option, opens the setup panel, runs journey ticks, taps a tempo, starts audio; fails on any script or WebGL error |
| `python3 tools/render.py ...` | Screenshot one world, or `--all` for a contact sheet; `--js` runs code inside the page |
| `python3 tools/thumbs.py [kind or name]` | Renders the choosers' pictures into `thumbs/` (needs Pillow and node) |
| `.venv-voice/bin/python tools/voice.py [--all]` | Makes the lessons' sound files in `voice/` from the words in `lang/` (needs node, ffmpeg, and the Python packages kokoro and soundfile) |
| `python3 tools/stereo.py a.png b.png` | For VR viewer pictures: how far blocks of the left half are from the right half, sideways and up and down (needs numpy) |

`tools/harness.py` explains the mechanism: it writes a temporary copy of `index.html` with a `<base>` pointing at the repository and one extra script that waits for the `mf-ready` event (sent by `main.js` after start-up) and then runs the test code inside `with(window.MF)`. It relies on the exact tag that loads `js/main.js` and asserts on it. Chrome is started with `--allow-file-access-from-files` so that modules load from `file://`.

Things to know about the headless environment:

- Rendering is software (SwiftShader), around ten frames per virtual second at full size. Use `--fast` and a larger `--budget` for anything involving feedback.
- Virtual time only advances while timers are pending. Drive tests with `setTimeout` steps; a `requestAnimationFrame` loop alone stalls.
- `dt` is capped at 50 ms per frame, so simulated time runs slower than virtual time.

`docs/worlds.jpg` is a contact sheet of all worlds from `render.py --all`.

### What has and has not been verified

Verified in headless Chrome: the VR viewer renders two lens-shaped pictures with the expected offset between them, with and without mirrors; every shader compiles; every motion, filter, overlay and transition renders; the journey engine, setup panel, file player and scrubber (both playback paths), tap tempo and spot links work without errors.

Not verified, because they need a real device or a human:

- Frame rate on phones. Bulbs, Julia and the Mandelbox worlds are the heaviest.
- The eye (section 8g) on a real screen: stills of it open and half shut were looked at, wide and tall. Nobody has watched it move: the blink's speed, how the pores look opening and shutting on a beat, whether the gaze turns the way the view does, how far the vessels move with real music, and what the extra pass costs a phone. A blink that changes the world waits, lids shut, while the new world's program is made if it was not made ahead of need.
- The lessons on a phone: dragging in the drawings, how fast step 5 paints, and the voice. Nobody has listened to the sound files; they were made and measured, not heard.
- Programs made ahead of need on a phone: how long it takes, and whether the picture keeps moving meanwhile (section 4).
- The lower start after a visit that ended while starting, on a device that really gives up.
- Multi-touch gestures. They cannot be simulated; the twist direction may feel reversed.
- How the built-in music sounds, and how strong each band's reaction should be.
- The change detector on real songs.
- Seeking in the streaming fallback on iOS, used for files over 15 minutes.
- Whether iOS keeps another app's music playing while the page is open in tap mode.
- Text entry in the setup panel on iOS (`user-select: text` is set on inputs because the body disables selection).
- Listening to a real Spotify or YouTube tab, and to a real microphone. Both paths were run in headless Chromium with simulated devices: the analyser received sound, the output stayed muted, and switching away released the stream. Whether Spotify's copy-protected audio reaches a shared tab stream, how strong the microphone gain of 3 should be, and what iOS does to another app's music when the microphone opens are unknown.
- Whether the steering handoff thresholds (0.08 and 0.5 rad/s, 0.7 s fade) suit a real head in a viewer. A head is never quite still, and sensor noise on a real phone is unknown.
- Whether the screen wake lock holds on a real phone with Journey or the VR viewer on, in Safari and as a home-screen web app.
- Everything about the VR viewer on a real phone: whether the two pictures merge through real lenses, whether the assumed pixel size is close enough, whether head turns go the right way in both landscape directions, and whether the autopilot is comfortable. The head-turn math is unit tested but the sensor conventions were taken from the specification, not from a device.
- The home-screen web app mode on iPhone (see section 2): that it opens without Safari's bars, and that the safe-area padding keeps the HUD clear of the notch and home bar.

## 15. Known weaknesses

- **Box and Fortress are grainy in flight.** Mandelbox detail is finer than the pixel-footprint threshold can tame. Hold still (section 8b) cleans a frame that is not moving; fewer iterations or a larger hit threshold for these two would help while flying.
- **The panel of controls has been seen only in headless Chrome**, which cannot be narrower than 500 pixels, so the sheet on a real phone (its height, its scrolling under a thumb, the safe areas) is untested. The buttons in it keep their old wording ("Surface plain"), not a name on the left and a setting on the right.
- **The dancers have been tuned from stills and numbers, never watched in motion or against real music by the author.** How steady a beat must be before they dance (`sure`) was set against made-up hits; a track with a very uneven bass line may leave them standing. With twelve figures the trails shader has 108 more uniform vectors and, where figures overlap, up to twelve sets of fourteen line distances a pixel; neither has been measured on a phone. A chip that allows fewer than about 160 fragment uniform vectors would fail to make the trails program at all.
- **The Fabric's waves are each page's own.** They come from that page's clock and sound, so a guest flying together and a recorded flight played back see other waves than the host or the recording did; places agree only across the cloth, not in height. To mend it the wave's time and five heights would have to be sent and recorded (`TG_KINDS`, `FL_KINDS`), with their checks. Its steepest waves at full sound are also near what the distance's 0.65 allows; if threads tear at loud moments, lower `FB_SND` or that number. No doorway opens there and inside out does nothing.
- **`tools/probe.py` passes partly by which places it asks about.** Inside a shape a distance means little, and there the chip and the script drift apart: asked about other places (a different run of chance numbers), Bulbs differs at one point in the grid and at two in the descent with mixed shapes, which is one more than the test allows. Adding the Fabric showed it, and the Fabric was given a run of numbers of its own so that the others are asked what they were before. The test should leave out places inside the shapes, or allow for them.
- **Motion strengths were tuned from stills.** Some are probably too strong or too subtle in motion.
- **Bulge is subtle; Scope and Orbit overlays can be faint** against bright worlds.

## 17. How the code came to be laid out this way

The app was one script in one closure. It was split in four steps, each done mostly by programs that parsed the code and moved text without rewriting it, and each checked with the smoke test, the probe test, the unit tests and renders:

1. **Files.** The script was cut along its section comments into modules. Start-up statements went into each file's `init()`; names set by more than one file went into one shared object.
2. **Owners.** The shared object was removed. Values were moved to the file that sets them, the few changes from outside became function calls, and the values that a frame changes in many places became the five state objects.
3. **The frame.** `frame()`, one function of 300 lines, was cut into the steps listed in section 3. The statements inside each step were not changed; each step begins by reading what it needs from the frame's notes and ends by leaving what later steps need.
4. **Homes.** Code that sat in the wrong file because of where the old comments fell was moved: palettes, Stats, orbs, share spots, pack worlds, the effect programs.

What could still be better:

- **The frame's notes are one shared record.** `fr` has about thirty fields, all declared with a comment in `loop.js`, but which step sets which is not checked. Steps that returned their results and took them as arguments would make the flow checkable.
- **The drawing steps set dozens of uniforms by hand.** A small table per program would shorten `render.js` and make a missed uniform harder.
- **`__dbg` is boilerplate.** It exists because the browser tests reach every name. Tests that import what they use would let it go.
- **`init()` order still matters** for a few files (the lists must be filled before a world is chosen, the library must load before templates are read). The order is the one in `main.js`.

Keeping each world's GLSL next to its JavaScript `de` is worth preserving in any layout, because they must change together.
